# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Язык проекта

Код, комментарии, имена тестов, сообщения бота и коммиты — **на русском**. Английские
идентификаторы допустимы только там, где так называется внешний контракт (`sendMessage`,
`chat_id`). Тесты называются фразой, описывающей поведение: `test('повторное нажатие
«открыть свою МДГ» заявку не дублирует', ...)`.

Комментарии объясняют **почему**, а не что. В этом коде почти каждый нетривиальный
комментарий фиксирует грабли, на которые уже наступали, — не удаляйте их, не разобравшись.

## Команды

```bash
npm test                       # весь набор (vitest run)
npm run test:watch             # тесты в watch-режиме
npx vitest run tests/fsm.spec.ts                   # один файл
npx vitest run -t 'часть имени теста'              # один тест по имени
npm run typecheck              # tsc --noEmit, обязателен перед коммитом
npm run build                  # tsc в dist/
npm run dev                    # бот локально (tsx watch)
npm run import:spreadsheet     # перенос dashboard/data.json в базу
```

Линтера в проекте нет — стиль держится на `tsc` со `strict` и на ревью.

### База для тестов

Тестам нужен живой Postgres на **порту 5433**. `docker-compose.dev.yml` — это оверрайд, сам
по себе он не запускается, нужны оба файла:

```bash
docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d db
```

Хелпер `tests/helpers/testDb.ts` сам создаёт отдельную базу `church40_test` и накатывает
миграции; адрес переопределяется через `TEST_DATABASE_URL`.

**Ловушка в выводе vitest.** Если база не поднята, файлы с тестами базы падают на `beforeAll`,
а сами тесты в них показываются как **skipped**. Итоговая строка `Tests … passed` выглядит
зелёной — судить надо по строке `Test Files`, там будет `failed`. Не обрезайте вывод так,
чтобы её не видеть.

В `vitest.config.ts` стоит `fileParallelism: false` — файлы делят одну тестовую базу и
параллельно идти не могут. `truncateAll()` в `beforeEach` чистит таблицы и сбрасывает
`registration_no_seq`, иначе ожидания «№1» ломаются.

## Архитектура

### Два процесса, одна база

Из одного образа запускаются два сервиса (см. `docker-compose.yml`):

- **bot** (`src/index.ts`) — опрос платформ, диалоги, рассылки. **Только он накатывает
  миграции** при старте.
- **dashboard** (`src/dashboard/index.ts`) — HTTP-сервер страницы администрирования.
  Миграции не накатывает.

Отсюда правило выкладки: **сначала бот, потом дашборд.** Иначе дашборд обратится к схеме,
которой ещё нет.

### Платформы за одним контрактом

`src/core/platform.ts` описывает интерфейс `Platform`; его реализуют
`src/adapters/telegram.adapter.ts` (grammY) и `src/adapters/max.adapter.ts`
(`@maxhub/max-bot-api`). Вся остальная логика платформ не знает: она получает
`IncomingUpdate` и возвращает `OutAction`.

Различия платформ живут только в адаптерах. Примеры, которые полезно знать заранее:
reply-клавиатур в MAX нет — меню служителя там рисуется инлайн-кнопками с префиксом
`ADMIN_CB`; телефон в Telegram приходит контактом, в MAX — визиткой VCF; диплинков в MAX нет,
поэтому `deepLink()` возвращает `null` и в QR попадает номер регистрации.

**У обеих библиотек цикл опроса умирает на любой ошибке**, поэтому его оборачивает
`src/adapters/polling.ts` (`supervisePolling`): перезапускает и после исключения, и после
молчаливого выхода. Для MAX перед перезапуском обязателен `bot.stop()` — иначе внутренний
флаг `pollingIsStarted` остаётся поднятым и повторный `start()` молча ничего не делает.

### Анкета участника — чистая функция

`src/core/fsm.ts` — единственное место, где решается, что ответить участнику.
`handleUpdate(input)` ничего не делает с миром: возвращает
`{ actions, state, draft, effects }`. Побочные действия выполняет `src/core/router.ts`,
разбирая `effects` (`save`, `finish`, `create_request`).

Поэтому логику диалога тестируют без базы и без сети (`tests/fsm.spec.ts`), а через
роутер — только сквозные пути. Новую проверку добавляйте так же: данные, которые нужны для
решения, приходят в `FsmInput` (роутер их вычисляет заранее), а не запрашиваются из FSM.

### Работа служителя

`src/core/flows/admin.flow.ts` — команды и мини-диалоги служителя, состояние диалога в
`admin_sessions`. `src/admin/menu.ts` — клавиатура и `RETIRED_LABELS`.

Про `RETIRED_LABELS` важно: reply-клавиатура живёт в клиенте Telegram, у служителей она
остаётся старой, пока бот не пришлёт новую. Нажатие на исчезнувшую подпись — обычный текст,
и без этого списка он ушёл бы в анкету как ответ на вопрос. **Убирая кнопку, переносите её
подпись в `RETIRED_LABELS`; возвращая — убирайте оттуда.** Тест на пересечение это ловит.

### Дашборд

Одна страница `dashboard/home-groups.html` (~113 КБ: вёрстка, стили и скрипт в одном файле), которую
`src/dashboard/server.ts` отдаёт по `/groups` за паролем. Данные **вшиваются в страницу на
сервере**: `withLive()` вставляет `window.HG_LIVE` и `window.HG_BASE` перед первым
`<script>`. Запроса за данными с клиента нет.

Что из этого следует:

- Относительные пути в `fetch` брать только от `window.HG_BASE`. Страница живёт на `/groups`
  без косой черты, поэтому относительный путь уходит в корень — на эти грабли уже наступали.
- Правки данных — POST-маршруты (`/group/create`, `/request/update`, `/group/delete`, …).
  CSRF-токена нет намеренно: кука `SameSite=Lax` на межсайтовый POST не уходит, а мутирующие
  маршруты отвечают 404 на всё, кроме POST.
- Разбор форм вынесен в `src/dashboard/forms.ts` чистыми функциями — так он покрывается
  тестами без HTTP.
- Лимит тела 64 КБ: кириллица в URL-кодировке занимает 6 байт на символ.
- Файл вшит в образ (`COPY dashboard/home-groups.html`), поэтому правка требует пересборки
  сервиса `dashboard`.

### База и репозитории

`src/db/repos/*.repo.ts` — по репозиторию на сущность, SQL внутри, наружу типы. Миграции —
обычный SQL в `migrations/`, применяются по порядку имени файла, каждая в своей транзакции,
учёт в `schema_migrations`. Нумерация обязана продолжать существующую (`009_…`).

Две ловушки, зафиксированные в коде:

- **`src/db/pool.ts` парсит `DATE` в строку**, а не в `Date`. Иначе `toISOString()` в
  плюсовой зоне (Europe/Moscow) уводит дату на день назад.
- **Происхождение записей** (`groups.source`, `requests.origin`: `таблица` / `бот` / `ui`).
  Любая правка или удаление в дашборде переводит запись из `таблица` в `ui`, и повторный
  перенос Google-таблицы (`scripts/import-spreadsheet.mjs`) её не затирает и не возвращает
  удалённое. Не ломайте это при изменении мутаторов.
- **Очистка базы служителем** (`maintenance.repo.ts`) удаляет заявки выборочно
  (`origin = 'бот'`), а не `TRUNCATE`: в `requests` лежат импортированные строки церкви.
  `groups` и `coordinators` в список очистки не добавлять.

### Рассылки

`src/broadcast/scheduler.ts` раз в сутки берёт материал дня и через `sender.ts` рассылает с
ограничением частоты (`throttle.ts`), фиксируя доставки в `deliveries`. День кампании
считается от `CAMPAIGN_START_DATE` (`schedule.ts`).

## Тесты

Проект писался по TDD, и это стоит продолжать: сначала падающий тест, потом код. Отдельно
принято **проверять тест мутацией** — сломать реализацию и убедиться, что падает именно он.
В истории уже были тесты, проходившие вхолостую (проверяли команду, которой больше нет).

Тесты на дашборд-страницу читают настоящий `dashboard/home-groups.html`
(`tests/dashboardRequestStatuses.spec.ts`) — так домен статусов не расходится с UI.

## Настройки

`src/config.ts` проверяет переменные окружения через zod и падает при старте, если чего-то
не хватает. Список с пояснениями — в `.env.example`. Значения, которые меняют поведение чаще
других: `ENABLED_PLATFORMS`, `ALLOW_DB_RESET` (показывает служителю кнопку очистки базы),
`MAX_API_URL` (по умолчанию `platform-api.max.ru`: заявленный SDK хост `platform-api2` не
отвечает), `CAMPAIGN_START_DATE`, `BROADCAST_TIME`.
