# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Язык проекта

Код, комментарии, имена тестов, сообщения бота и коммиты — **на русском**. Английские
идентификаторы допустимы только там, где так называется внешний контракт (`sendMessage`,
`chat_id`). Тесты называются фразой, описывающей поведение: `test('повторное нажатие
«открыть свою МДГ» заявку не дублирует', ...)`.

Комментарии объясняют **почему**, а не что. В этом коде почти каждый нетривиальный
комментарий фиксирует грабли, на которые уже наступали, — не удаляйте их, не разобравшись.

## Процесс разработки

Вся разработка идёт **через пулл-реквесты**: так сохраняется история и видно, кто и когда
вносил изменения. Прямых пушей в основную ветку нет. Работаем в отдельной ветке, а в основную
ветку изменения попадают только через PR. PR создаём по просьбе пользователя, не по своей
инициативе.

## Команды

```bash
npm test                       # весь набор (vitest run)
npm run test:watch             # тесты в watch-режиме
npx vitest run tests/fsm.spec.ts                   # один файл
npx vitest run -t 'часть имени теста'              # один тест по имени
npm run typecheck              # tsc --noEmit, обязателен перед коммитом
npm run build                  # tsc в dist/
npm run dev                    # бот локально (tsx watch)
npm run import:spreadsheet     # перенос dashboard/data.json в базу
```

Линтера в проекте нет — стиль держится на `tsc` со `strict` и на ревью.

### База для тестов

Тестам нужен живой Postgres на **порту 5433**. `docker-compose.dev.yml` — это оверрайд, сам
по себе он не запускается, нужны оба файла:

```bash
docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d db
```

Хелпер `tests/helpers/testDb.ts` сам создаёт отдельную базу `church40_test` и накатывает
миграции; адрес переопределяется через `TEST_DATABASE_URL`.

**Ловушка в выводе vitest.** Если база не поднята, файлы с тестами базы падают на `beforeAll`,
а сами тесты в них показываются как **skipped**. Итоговая строка `Tests … passed` выглядит
зелёной — судить надо по строке `Test Files`, там будет `failed`. Не обрезайте вывод так,
чтобы её не видеть.

В `vitest.config.ts` стоит `fileParallelism: false` — файлы делят одну тестовую базу и
параллельно идти не могут. `truncateAll()` в `beforeEach` чистит таблицы и сбрасывает
`registration_no_seq`, иначе ожидания «№1» ломаются.

## Экономия контекста и времени

Полный прогон и чтение больших файлов целиком — самое дорогое в работе с проектом. Правила:

- **Тесты — сначала только затронутые.** Пока идёт работа, гоняйте изменённые файлы
  (`npx vitest run tests/имя.spec.ts`, в интерфейсе — `cd web/home-groups && npx vitest run src/features/…`)
  или один тест по имени (`-t '…'`). Полный набор (`npm test` и `npx vitest run` в `web/home-groups`)
  — один раз перед коммитом. Вывод фильтруйте, но строку `Test Files` оставляйте (см. ловушку выше):
  `… 2>&1 | grep -E "^\s+×|Test Files|Tests "`.
- **Большие файлы не читать целиком — искать по ним.** `dashboard/home-groups.html` (~178 КБ, вся
  страница старого дашборда одним файлом), `dashboard/data.json` (~190 КБ, выгрузка таблицы церкви),
  `web/home-groups/src/shared/i18n/ru.ts` (~1700 строк, все подписи интерфейса),
  `src/home-groups/contracts.ts` (~1400 строк), `src/home-groups/api/views.ts` (~1000 строк),
  `package-lock.json`. Находите нужное через `grep -n` и читайте окно вокруг строки
  (`sed -n 'N,Mp'` или Read с `offset`/`limit`).
- **Сначала поиск, потом чтение.** Где живёт поле или подпись, быстрее узнать `grep -rn` по `src/`,
  `web/home-groups/src/`, `tests/` и `migrations/`, чем читать модули подряд. Сводка устройства —
  в этом файле и в README: начинайте с них, а не с обхода кода.
- **Проверка типов дешевле тестов.** После правки контракта (`contracts.ts`) или типов сначала
  `npm run typecheck` и `cd web/home-groups && npx tsc --noEmit`: они за секунды покажут все места,
  которые надо поправить (фикстуры, спеки), без прогона тестов.

## Архитектура

### Два процесса, одна база

Из одного образа запускаются два сервиса (см. `docker-compose.yml`):

- **bot** (`src/index.ts`) — опрос платформ, диалоги, рассылки. **Только он накатывает
  миграции** при старте.
- **dashboard** (`src/dashboard/index.ts`) — HTTP-сервер страницы администрирования.
  Миграции не накатывает.

Отсюда правило выкладки: **сначала бот, потом дашборд.** Иначе дашборд обратится к схеме,
которой ещё нет. Это делает `scripts/deploy.sh`; CI (`.github/workflows/ci.yml`) гоняет
`typecheck` и тесты на PR, а после мержа в `main` сам заходит на сервер по SSH, делает
`git pull` и вызывает `deploy.sh`. Бэкап — отдельный systemd-таймер (`deploy/systemd/`).

**Боевой `.env` живёт только на сервере и в git не входит.** Новая обязательная переменная
окружения (как `DASHBOARD_SUPER_PASSWORD`) требует дописать её в серверный `.env` **до**
мержа: иначе сервис после деплоя не стартует. Копировать `.env` между машинами вслепую нельзя.

### Платформы за одним контрактом

`src/core/platform.ts` описывает интерфейс `Platform`; его реализуют
`src/adapters/telegram.adapter.ts` (grammY) и `src/adapters/max.adapter.ts`
(`@maxhub/max-bot-api`). Вся остальная логика платформ не знает: она получает
`IncomingUpdate` и возвращает `OutAction`.

Различия платформ живут только в адаптерах. Примеры, которые полезно знать заранее:
reply-клавиатур в MAX нет — меню служителя там рисуется инлайн-кнопками с префиксом
`ADMIN_CB`; телефон в Telegram приходит контактом, в MAX — визиткой VCF; диплинков в MAX нет,
поэтому `deepLink()` возвращает `null` и в QR попадает номер регистрации.

**В MAX id чата не равен id человека** (человек 27637540 — чат 428149719), а в Telegram у
личной переписки они совпадают. `ADMIN_IDS` — это id людей, поэтому писать служителю надо в
чат: `users.chatIds()` отдаёт его по запомненному `chat_id`. Так же и `canReach()`. Чат мы
узнаём только из входящего апдейта, так что после очистки базы уведомления в MAX замолчат,
пока служитель снова не напишет боту; `/admins` это показывает.

Ещё в MAX подтверждение нажатия требует текста: пустой `answerOnCallback` отвечает
`400 message or notification required`. Ошибка косметическая, пишется в `debug`.

**У обеих библиотек цикл опроса умирает на любой ошибке**, поэтому его оборачивает
`src/adapters/polling.ts` (`supervisePolling`): перезапускает и после исключения, и после
молчаливого выхода. Для MAX перед перезапуском обязателен `bot.stop()` — иначе внутренний
флаг `pollingIsStarted` остаётся поднятым и повторный `start()` молча ничего не делает.

### Параллельная обработка апдейтов

Библиотеки опроса ждут обработчик, поэтому без очереди сто человек стояли бы друг за другом.
`src/core/updateQueue.ts` (`UpdateQueue`, подключён в `src/index.ts`) обрабатывает до 16
апдейтов одновременно, а апдейты **одного человека** (ключ `платформа:id`) — строго по
порядку: анкета читает и пишет его состояние целиком, два шага разом перетёрли бы друг друга.
`submit()` возвращается, когда апдейт принят, а не обработан; когда места кончились, он
ждёт, и опрос притормаживает сам. Пул соединений с базой (`src/db/pool.ts`) — 20, больше
лимита очереди. Не ставьте внутрь `Router.handle` долгие ожидания: они занимают место.

Для этого `Router` в боте создаётся с `backgroundNotify: true`: уведомления служителям
(`AdminNotifier`) уходят в фоне, при 429 повторяются до пяти раз с паузой платформы.
В тестах режим выключен, и `handle` ждёт отправки. При остановке бот делает
`queue.idle()` и `router.drain()`. Сквозной тест на 100 анкет — `tests/concurrentUsers.spec.ts`.

### Анкета участника — чистая функция

`src/core/fsm.ts` — единственное место, где решается, что ответить участнику.
`handleUpdate(input)` ничего не делает с миром: возвращает
`{ actions, state, draft, effects }`. Побочные действия выполняет `src/core/router.ts`,
разбирая `effects` (`save`, `finish`, `create_request`).

**Любой ответ про Малую группу заводит заявку** (`mdgRequestType()` в `fsm.ts`: join →
`join_group`, open/home → `lead_group`, member → `already_member`, leader →
`already_leader`) — и в боте, и при ручной регистрации в дашборде (там `origin='ui'`).
Не вводите ветки, где заявки нет: такие регистрации пропадают из «Заявок».

Поэтому логику диалога тестируют без базы и без сети (`tests/fsm.spec.ts`), а через
роутер — только сквозные пути. Новую проверку добавляйте так же: данные, которые нужны для
решения, приходят в `FsmInput` (роутер их вычисляет заранее), а не запрашиваются из FSM.

### Работа служителя

`src/core/flows/admin.flow.ts` — команды и мини-диалоги служителя, состояние диалога в
`admin_sessions`. `src/admin/menu.ts` — клавиатура и `RETIRED_LABELS`.

Про `RETIRED_LABELS` важно: reply-клавиатура живёт в клиенте Telegram, у служителей она
остаётся старой, пока бот не пришлёт новую. Нажатие на исчезнувшую подпись — обычный текст,
и без этого списка он ушёл бы в анкету как ответ на вопрос. **Убирая кнопку, переносите её
подпись в `RETIRED_LABELS`; возвращая — убирайте оттуда.** Тест на пересечение это ловит.

### Дашборд

Одна страница `dashboard/home-groups.html` (~178 КБ: вёрстка, стили и скрипт в одном файле), которую
`src/dashboard/server.ts` отдаёт по `/groups` за паролем. Данные **вшиваются в страницу на
сервере**: `withLive()` вставляет `window.HG_LIVE` и `window.HG_BASE` перед первым
`<script>`. Запроса за данными с клиента нет.

Что из этого следует:

- Относительные пути в `fetch` брать только от `window.HG_BASE`. Страница живёт на `/groups`
  без косой черты, поэтому относительный путь уходит в корень — на эти грабли уже наступали.
- Правки данных — POST-маршруты (`/group/create`, `/request/update`, `/group/delete`, …).
  CSRF-токена нет намеренно: кука `SameSite=Lax` на межсайтовый POST не уходит, а мутирующие
  маршруты отвечают 404 на всё, кроме POST.
- Разбор форм вынесен в `src/dashboard/forms.ts` чистыми функциями — так он покрывается
  тестами без HTTP.
- Лимит тела 64 КБ: кириллица в URL-кодировке занимает 6 байт на символ.
- Файл вшит в образ (`COPY dashboard/home-groups.html`), поэтому правка требует пересборки
  сервиса `dashboard` (деплоем или `docker compose up -d --build dashboard`).
- **Страница не импортирует код бота**, поэтому справочники продублированы: районы, статусы
  группы и заявки, категории возраста, форматы группы есть и в `src/core/groups.ts` /
  `texts.ts`, и в `home-groups.html` (`FORM_*`, `COMPOSITION_OPTIONS`). Меняя один список,
  меняйте оба.
- **После «Сохранить» страница перезагружается** (данные вшиты), но состояние (вкладка,
  фильтры, сортировка, прокрутка, раскрытые заявки) сохраняется через `reloadKeepingState()`
  и поднимается `restoreState()` в `sessionStorage`. Новый фильтр добавляйте в оба.
  Прямого `location.reload()` в странице быть не должно — тест это проверяет.
- **Темы** (тёмная, светлая, серая): все цвета — переменные палитры в начале файла, темы
  переопределяют их через `html[data-theme="…"]`. Не вшивайте цвета и `rgba(255,255,255,…)`
  в стили — используйте переменные (`--line-soft`, `--grid`, `color-mix(… var(--ok) …)`).
  Тема ставится скриптом в начале файла до стилей, чтобы не мигала.
- **Роли и удаление.** Два входа: `mbv_admin` (`DASHBOARD_PASSWORD`) и `super_mbv_admin`
  (`DASHBOARD_SUPER_PASSWORD`). Удалять может только `super`: адреса из `DELETE_PATHS` в
  `server.ts` отвечают 403 остальным, а страница получает `window.HG_CAN_DELETE` и прячет
  кнопки (`html[data-no-delete]`). **Заводя новый маршрут удаления, добавьте его в
  `DELETE_PATHS`** — иначе он будет открыт обычному входу. Роль хранится в сессии
  (`SessionService.roleOf`); без `DASHBOARD_SUPER_PASSWORD` дашборд не стартует.

### Новый интерфейс «Домашние группы» и отключение старого дашборда

Третий сервис — `home-groups` (`src/home-groups/`, интерфейс в `web/home-groups/`), порт 8092. Он заменил старый
дашборд: заявки (подбор, закрытие, возврат, «другие обращения»), справочник, регистрация, «Команда» и кампания.
Общий типовой контракт API — `src/home-groups/contracts.ts` (интерфейс импортирует из него только типы).
Старый дашборд вынесен в профиль compose `legacy` и отключается строкой `LEGACY_DASHBOARD=off` в `.env`
(`scripts/deploy.sh`); порядок перехода — `docs/ПЕРЕХОД-НА-НОВЫЙ-ИНТЕРФЕЙС.md`. Новый код пишем в новом сервисе;
в старый дашборд, кроме срочных исправлений, не возвращаемся. Вкладка «Наборы» (`features/kits/`, сервер `src/home-groups/kits.ts`) отмечает выдачу наборов по номеру регистрации
или ФИО — та же отметка `users.kit_issued_at`, что у бота; сканер QR убран до https (код — в истории, см. README). Помощник по разбору заявок открывается значком ✦ в строке инструментов «Заявок» (сводка и запуск подбора — под кнопкой «Подбор» там же и в «Настройки → Подбор», `MatchingPanel.tsx`): одно окно (`features/assistant-chat/AssistantChat.tsx`) с вкладками «Разбор заявок» и «Вопрос по базе»; модель к каждой записи пишет пояснение (`request_hints.note`), а заявку без ответа модели разобранной не считает. Переключатель автоподбора — в «Настройки → Подбор»; там же «Писать в MAX при утверждении»: `approve` ставит сообщения человеку и ведущему в `placement_notices` (миграция 065), отправляет их бот (`src/broadcast/placementNotices.ts`), ответы кнопками пишутся туда же; «Группа не подходит» от человека возвращает заявку в работу (`reopenDeclined`, бэкфилл 067), повтор ведущим без ФИО — `needs_fio_resend` (066) и кнопка в «Настройки → Подбор». В окне «Другая группа» — «Выбрать» (`choose`: предложение `source='manual'`, автоподбор его не трогает) и «Утвердить». Ролей команды пять (миграция 051: катализатор, старший распределитель, распределитель, старший координатор, координатор); незнакомое название `team_role_id` кладёт на одну из них. Направление группы — справочник `group_directions` (миграция 052, «Настройки → Направления», колонки `groups.format` больше нет); «Камерная группа» (`groups.chamber`) — людей не направляют, а адрес и телефоны сервер скрывает при выдаче групп (`contactsAccess.ts`, видят лидеры, её координатор и полный вход). Роли человека в команде — связи `coordinator_roles` со справочником
`team_roles` (миграция 049; ролей может быть несколько); что роль значит (распределитель, координатор, старший) решает
`team_roles.kind`, а не слова в названии — по названию роль не угадывайте. «Создать группу по заявке» связывает новую
группу с заявкой через `groups.source_request_id` — ту же связь, что у потенциальной группы из «хочу открыть». Ведущий и
соведущий группы — ссылки на людей из «Людей» (регистрация или карточка, миграции 030 и 054): в правке группы их только
выбирают (ФИО текстом не правится, имя и телефон показываются из карточки человека), а при создании группы вписанные ФИО
сразу заводят карточки. Из карточки человека его ставят в группу участником, ведущим или соведущим. «Люди» — сквозной справочник всех, кто связан с церковью: у каждой заявки есть человек (`requests.user_id`/`person_id`, миграция 057, склейка по телефону), данные человека читаются и правятся только в его записи, а поля самой заявки — снимок «как пришла»; участник команды («Координаторы») — тоже ссылка на человека (миграция 056, `coordinators.user_id`/`person_id`), его имя следует за ФИО человека триггером, который переписывает и `requests.responsible`, и `groups.coordinator` — имя по-прежнему ключ связи, не правьте его в обход. Пол человека — жёсткое условие подбора: мужчине не предлагают женскую группу и
наоборот (`exclusionReason`, пол группы — из «Состава»). Пол выводится из ФИО на лету (`src/core/gender.ts`), ручной и
подсказанный моделью хранятся в `person_genders` (миграция 055); неясный — пусто, такому человеку мужские и женские
группы не подбираются, а интерфейс подсвечивает «Пол не указан». Адрес группы виден всем, кто вошёл, и участвует в подборе (пустой — подбор по метро или ориентиру); при `YANDEX_GEOCODER_KEY` адреса геокодируются в фоне (`geocodeJob.ts`, кэш `geocode_cache`) и подбор считает расстояние. **Контакты видит тот, кто взял человека или группу на себя:** сервер скрывает их на
выходе по вошедшему (`contactsAccess.ts`: `requestsFor`, `groupsFor`, `peopleFor` и др.) — у чужих заявок, групп и людей
личный вход видит последние цифры телефона, без улицы (телефоны ведущих и соведущих некамерных групп — целиком); лидеры, старший распределитель и полный вход видят всё. Новое
представление или маршрут с телефонами и адресами пропускайте через тот же модуль, иначе они утекут личным входам.
`/registration` — «Стойка регистрации»: регистрация участника или группы и «Наборы», без остальных разделов. Уровень
входа `registration` («Пользователи и роли», миграция 053) пускает только туда и только на регистрацию участника и наборы:
API для него закрыт белым списком `deskAllows` в `server.ts` — **маршрут, нужный стойке, добавляйте туда**. Уровень
`readonly` («Только чтение», миграция 063) видит заявки, группы и людей, но ничего не меняет: белый список
`readonlyAllows` в `server.ts` (из POST — только `map/loaded` и поиск `kits/find|search`; закрыты `/team` и `settings/*`),
в интерфейсе — `useCanChange()` из `shared/access.ts`: **новую кнопку действия прячьте им же**. Карточку группы не правит
тот, у кого в команде только роль `distributor` (`mayEditGroups` на сервере, `useCanEditGroups` в интерфейсе).
Выданный пароль лежит и хешем (вход), и зашифрованным (`staff.password_sealed`, секрет как у ключей «Настроек») —
полный вход открывает его «глазиком» в «Пользователях и ролях», открытие пишется в журнал. В журнал
`audit_log` попадают названия полей и числа, но не имена и телефоны.

### База и репозитории

`src/db/repos/*.repo.ts` — по репозиторию на сущность, SQL внутри, наружу типы. Миграции —
обычный SQL в `migrations/`, применяются по порядку имени файла, каждая в своей транзакции,
учёт в `schema_migrations`. Нумерация обязана продолжать существующую (`009_…`).

Две ловушки, зафиксированные в коде:

- **`src/db/pool.ts` парсит `DATE` в строку**, а не в `Date`. Иначе `toISOString()` в
  плюсовой зоне (Europe/Moscow) уводит дату на день назад.
- **Происхождение записей** (`groups.source`, `requests.origin`: `таблица` / `бот` / `ui`).
  Любая правка или удаление в дашборде переводит запись из `таблица` в `ui`, и повторный
  перенос Google-таблицы (`scripts/import-spreadsheet.mjs`) её не затирает и не возвращает
  удалённое. Не ломайте это при изменении мутаторов.
- **Удаление в дашборде мягкое** (`archived_at`) для групп, заявок и координаторов; жёсткое —
  только у регистраций (`users.delete`, каскад на сессии, заявки и рассылки). Восстановить
  мягко удалённое можно только правкой базы (`UPDATE … SET archived_at = NULL`).
- **Бэкфилл-миграции.** Данные, пропущенные багом, дозаводятся миграцией (пример:
  `016_backfill_requests_for_registrations.sql`), идемпотентной, с тестом на её SQL.
- **Очистка базы служителем** (`maintenance.repo.ts`) удаляет заявки выборочно
  (`origin = 'бот'`), а не `TRUNCATE`: в `requests` лежат импортированные строки церкви.
  `groups` и `coordinators` в список очистки не добавлять.

### Рассылки

`src/broadcast/scheduler.ts` раз в сутки берёт материал дня и через `sender.ts` рассылает с
ограничением частоты (`throttle.ts`), фиксируя доставки в `deliveries`. День кампании
считается от `CAMPAIGN_START_DATE` (`schedule.ts`).

## Тесты

Проект писался по TDD, и это стоит продолжать: сначала падающий тест, потом код. Отдельно
принято **проверять тест мутацией** — сломать реализацию и убедиться, что падает именно он.
В истории уже были тесты, проходившие вхолостую (проверяли команду, которой больше нет).

Тесты на дашборд-страницу читают настоящий `dashboard/home-groups.html`
(`tests/dashboardHomeGroups.spec.ts`, `tests/dashboardRequestStatuses.spec.ts`) строковыми
проверками по окнам `html.slice(…)`. Когда код в окне растёт, окно нужно расширять, иначе
тест тихо перестаёт видеть искомое. Проверка на сервере (роли, формы, маршруты) — в
`dashboardRoles.spec.ts`, `dashboardServer.spec.ts`, `dashboardCreateIntegration.spec.ts`.

## Настройки

`src/config.ts` проверяет переменные окружения через zod и падает при старте, если чего-то
не хватает. Список с пояснениями — в `.env.example`. Значения, которые меняют поведение чаще
других: `ENABLED_PLATFORMS`, `ALLOW_DB_RESET` (показывает служителю кнопку очистки базы),
`MAX_API_URL` (по умолчанию `platform-api.max.ru`: заявленный SDK хост `platform-api2` не
отвечает), `CAMPAIGN_START_DATE`, `BROADCAST_TIME`.
