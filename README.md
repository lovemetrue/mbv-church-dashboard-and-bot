# Бот-ассистент МБВ

Один бот для двух мессенджеров: Telegram и MAX. Регистрирует участников церковной кампании,
передаёт заявки служителям и каждый день рассылает материал дня.

Код общий: сценарий, тексты и база данных одни и те же, различия платформ спрятаны в двух адаптерах.
Рядом с ботом работает **дашборд** (мини-CRM для служителей): заявки, домашние группы, регистрация,
участники, аналитика и статистика кампании. Бот и дашборд — два сервиса из одного образа
на одной базе (см. [Дашборд](#дашборд-домашних-групп)).
Платформы включаются переменной `ENABLED_PLATFORMS`, поэтому можно запустить Telegram сегодня,
а MAX добавить позже, когда выдадут токен, ничего не переписывая.

## Что делает бот

**Регистрация** идёт по ТЗ церкви:

1. Приветствие с перечнем собираемых данных и ссылками на положение и политику обработки
   персональных данных. Без согласия анкета не начинается.
2. Обязательные вопросы: ФИО, телефон (кнопка «Поделиться номером» или ввод руками),
   церковь (филиалы МБВ, другая церковь, не посещаю).
3. Тем, кто из МБВ, задаётся вопрос про домашнюю группу, и дальше ветка зависит от ответа:

| Ответ | Уточняющие вопросы | Тип заявки служителю |
| --- | --- | --- |
| Хочу присоединиться | район, возраст, удобное время и адрес (по желанию) | хочет в домашнюю группу |
| Готов открыть Малую группу / дать дом | район, возраст, время встреч и адрес (по желанию) | готов открыть группу |
| Уже состою | ФИО ведущего, возраст | уже состоит в группе |
| Веду группу | нет | уже ведёт группу |

**Любой ответ про группу заводит заявку**, даже «уже состою» и «веду»: служитель сверяет
человека с реестром групп. Раньше заявки не было у тех, кто уже в группе, и такие регистрации
не попадали в дашборд. То же правило действует и для регистрации, заведённой служителем
в дашборде (там заявка помечена `origin='ui'`). Соответствие ответа и типа заявки одно на оба
пути — `mdgRequestType()` в [src/core/fsm.ts](src/core/fsm.ts).

4. Сводка со всем, что человек сообщил, и подтверждение (заявка создаётся на этом шаге).
5. Номер регистрации и QR-код, по которому выдаётся набор участника.

Ответы пишутся в базу **по шагам**: если человек бросит анкету, у церкви всё равно останутся
телефон и ФИО. На любом уточняющем вопросе есть кнопка «Завершить регистрацию»: номер присвоится,
но анкета будет помечена неполной, а человек сможет дозаполнить её позже кнопкой в меню.

**Меню участника** (кнопки, доступны после регистрации):

- 📋 Проверить статус (ждёте направления в домашнюю группу или можете получить набор)
- 🏠 Открыть свою домашнюю группу
- 📝 Дозаполнить анкету (только если регистрация неполная)

Переписки с участниками в боте нет: он присылает материалы кампании и передаёт заявки
служителям. Если человек напишет боту свободный текст, бот честно скажет, что сообщения
не читает, и покажет кнопки.

Каждая заявка приходит служителям в бот с именем, телефоном, районом и возрастом и ссылкой
«Открыть заявку в дашборде». Служитель звонит человеку по телефону из заявки, а затем ведёт её
в дашборде: меняет статус, назначает ответственного и группу. Команд `/requests` и `/close`
в боте больше нет. Если платформа отвечает «слишком часто» (пачка заявок разом), уведомление
повторяется до пяти раз с паузой, которую назвала платформа.

Повторные нажатия заявку не дублируют: пока лежит незакрытая заявка того же вида,
человеку отвечают, что она уже в работе. После исполнения или аннулирования заявку можно
подать снова.

**Ежедневная рассылка.** В `BROADCAST_TIME` по московскому времени всем участникам уходит материал
дня кампании. День считается от `CAMPAIGN_START_DATE`. Материалы загружает служитель командой `/setday`.

## Быстрый старт на ноутбуке

Нужен Docker Desktop и токен Telegram-бота.

1. **Получить токен Telegram**: написать [@BotFather](https://t.me/BotFather), команда `/newbot`,
   придумать имя и адрес бота, скопировать токен.

2. **Настроить `.env`**:

```bash
cp .env.example .env
```

Заполнить `BOT_TOKEN_TELEGRAM`, `CAMPAIGN_START_DATE` и `POSTGRES_PASSWORD`.

3. **Запустить**:

```bash
docker compose up -d --build
```

4. **Прописать администраторов.** В `ADMIN_IDS_TELEGRAM` через запятую только числовые id:
   `1763357182,1124093101`. Каждый служитель узнаёт свой id командой `/whoami` в боте.
   Username там не работает: по нему Bot API не умеет писать в личку, права были бы,
   а уведомления о заявках молча не доходили бы. Нечисловые записи бот пропускает
   и сообщает об этом в логе при старте. Затем:

```bash
docker compose up -d
```

Логи: `docker compose logs -f bot`

### Разработка с горячей перезагрузкой

```bash
docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d db
npm install
npm run dev
```

В этом режиме база доступна с хоста на порту 5433, `DATABASE_URL` в `.env` уже настроен на него.

Тесты и проверка типов (тестам нужен Postgres на порту 5433, он поднимается командой выше;
если базы нет, файлы с тестами базы падают, а сами тесты показываются как skipped, поэтому
смотрите строку `Test Files`, а не только `Tests`):

```bash
npm test
npm run typecheck
```

## Что делает служитель в боте

В боте осталось то, что умеет только бот. Всё остальное — статистика, заявки, домашние
группы и ведущие — в дашборде: http://5.23.48.25:8090/groups (своего домена пока нет)

На клавиатуре то, чем служитель пользуется с телефона — набирать это командами неудобно:

| Кнопка | Команда | Что делает |
| --- | --- | --- |
| 📦 Выдать набор | `/kit` | спросит номер регистрации или ФИО, покажет карточку участника и отметит выдачу |
| 📣 Объявление | `/broadcast` | спросит текст, покажет число получателей, отправит после подтверждения |
| ✏️ Загрузить день | `/setday` | спросит номер дня и текст материала |
| 📝 Дослать вопросы | `/extra` | зарегистрированным с заявкой «хочу в группу» или «готов открыть» шлёт приглашение с двумя вопросами (время и адрес); покажет число получателей и отправит после подтверждения; см. «Досылка вопросов» ниже |
| ▶️ Старт | `/start` | начать заново |
| 🧹 Очистить базу | `/reset` | только при `ALLOW_DB_RESET` |

Кнопка и команда — один и тот же диалог: `/kit 42` отмечает сразу, а `/kit` без номера спрашивает
его следующим сообщением. Быстрее всего набор выдаётся сканированием QR-кода участника — кнопка
нужна, когда QR не показать. Остальное — командами:

| Команда | Что делает |
| --- | --- |
| `/getday <день>` | показать материал дня |
| `/sendday <день>` | отправить материал дня прямо сейчас |
| `/days` | какие дни уже загружены |
| `/export` | выгрузка участников в CSV |
| `/admins` | кто видит клавиатуру служителя |
| `/whoami` | свой числовой id для `ADMIN_IDS` |
| `/help` | этот список |

**Почему рассылки и наборы остались в боте.** Отправлять сообщения умеет только процесс
бота — у дашборда нет доступа к платформам. А QR-код участника это диплинк `t.me/...?start=kit_N`:
служитель наводит камеру, открывается бот и отмечает выдачу.

**Убраны:** `/stats` (уехала в раздел «40 дней» дашборда), `/requests` и `/close` (заявки
ведутся в дашборде), `/leader`, `/leaders`, `/register` (заводится в дашборде).

Reply-клавиатура живёт в клиенте, поэтому у служителей она останется старой, пока бот не
пришлёт новую. Нажатие на исчезнувшую кнопку бот распознаёт и объясняет, куда всё переехало,
— иначе подпись кнопки ушла бы в анкету как ответ на вопрос (`RETIRED_LABELS` в
[src/admin/menu.ts](src/admin/menu.ts)).

## Вопросы от участников

После регистрации в меню есть кнопка «💬 Задать вопрос». Человек нажимает, пишет вопрос одним
сообщением — заявка типа `question` уходит служителям тем же уведомлением, что и заявки на группу,
и видна в дашборде. На шаге вопроса есть «Отмена»: передумать можно в любой момент.

Вопрос короче пяти знаков не принимается — «?» служителю ничего не объясняет.

**Вопросов можно задать несколько, но не больше трёх неотвеченных одновременно.** Здесь другая
логика, чем у заявок на группу: там запрет на повторную заявку, потому что вторая заявка на ту же
группу смысла не имеет, а вопросы бывают разные и по одному не исчерпываются. Предел нужен, чтобы
один человек не завалил служителей очередью. Как только служитель закрывает заявку в дашборде,
место освобождается. Значение предела — `MAX_OPEN_QUESTIONS` в [src/core/fsm.ts](src/core/fsm.ts).

## Домашние группы и ведущие

Группы ведутся **в дашборде** (вкладки «Домашние группы» и «Добавить»); команды бота `/leader`
и `/leaders` убраны. Исходные данные пришли из Google-таблицы церкви (импорт — ниже),
дальше группы правят прямо на странице.

В таблице групп: № (код `ДГ-0001`), ведущий и соведущий второй строкой, «40 дней», возраст,
участники, район, адрес, **формат группы** (цветные метки: смешанная — зелёная, мужская — синяя,
женская — розовая, ментальная — коричневая, семейная — жёлтая, служение и приватная — серые),
«Приём новых» (да / нет / по требованию), «Проверено», статус. Телефон, координатор, обратная
связь, День, Время и прочее — в раскрывающейся строке. Фильтры: статус группы (галочки, можно
несколько: «Действующие», «Потенциальная», «На паузе», «Закрытые», «Недвижимость», «Кампания»),
отдельная галочка «40 дней» и список координаторов.

Статусы группы: `Функционирует`, `Потенциальная`, `На паузе`, `Закрыта`, `Недвижимость`,
`Кампания` (как «Функционирует», но группа работает только на время кампании; ведущий такой
группы считается ведущим действующей). Значения района и статуса — списки в
[src/core/groups.ts](src/core/groups.ts); дашборд группирует записи по ним напрямую, поэтому
свободный текст вместо выбора развалил бы статистику.

«Потенциальная» группа заводится по заявке «хочу открыть» / «дам дом». Ответы бота про адрес и удобное время (в анкете или потом, при досылке)
переносит в группу функция `sync_potential_group` (миграция 035): адрес — в поле «Адрес», если оно пустое, время — строкой «Удобное время: …» в комментарий.
День и время суток свободным текстом не разобрать, их координатор заполняет сам.

В форме правки возраст группы выбирается из категорий кампании (до 18, 18-25, 25-40, 40-55,
55-65, 65+); нестандартное значение, которое уже стоит у группы («35-50», «любой»), остаётся
пунктом списка и не теряется. «Формат группы» отмечается галочками, можно несколько
(хранится в колонке `composition` через запятую).

Удаление группы мягкое: запись пропадает со страницы, но остаётся в базе (`archived_at`).
Вернуть её можно только правкой базы — кнопки восстановления в интерфейсе нет.

## Регистрация участника служителем

Вкладка «Регистрация» в дашборде: служитель заполняет анкету за человека, который в боте не
сидит (ФИО, телефон, церковь, ответ про малую группу, предпочтительный способ связи и
комментарий). Ответ про группу заводит заявку так же, как анкета бота. Отдельная ссылка
`/registration` открывает **только форму** (без списка и телефонов), её можно давать шире,
чем пароль от всего дашборда. У такой записи нет чата с ботом, поэтому рассылки ей не
отправляются — в выгрузке она помечена как заведённая служителем. Колонка «Выдан набор»
показывает, получен ли набор (зелёное «Да» / красное «Нет»); у регистрации есть QR и
печатная карточка.

## Хранение истории заявок

Закрытые заявки удаляются через `REQUESTS_RETENTION_DAYS` дней (по умолчанию 90, около трёх
месяцев). Чистка идёт раз в сутки, первым делом на тике планировщика — независимо от того,
началась кампания или уже закончилась. Сколько удалено, видно в логе.

**Открытые заявки не удаляются никогда**, даже очень старые. Старая открытая заявка это не
история, а человек, которому забыли позвонить: стирать единственный след обращения нельзя.
Все открытые заявки видны в дашборде (вкладка «Заявки»).

Участники и материалы кампании ротации не подлежат — это рабочий реестр церкви. Если понадобится
удалять и персональные данные по сроку, это отдельная задача: там нужно решить, что делать
с номерами регистрации и выданными наборами.

## Выдача наборов и QR-код

После регистрации участник получает номер и QR-код. В QR лежит ссылка вида
`t.me/<бот>?start=kit_42`: служитель наводит камеру телефона, у него открывается бот
и набор отмечается выданным. Bot API сам QR не читает, поэтому сканером служит камера.

Второй путь без QR: кнопка «📦 Выдать набор» → номер регистрации или ФИО. Если по ФИО нашлось
несколько человек, бот покажет список с номерами и попросит уточнить — наугад не выдаёт.
Повторная выдача не проходит молча: бот скажет, что набор уже выдан, и когда.

В MAX диплинков нет, поэтому там в QR попадает сам номер регистрации, а служитель вводит его руками.

## Очистка базы на время тестов

При `ALLOW_DB_RESET=true` у служителей появляется кнопка «🧹 Очистить базу»: она удаляет
участников, заявки, материалы дней и журнал рассылок, а нумерацию регистраций возвращает
к единице. Схема, миграции и настройки не затрагиваются.

Две защиты, потому что действие необратимое:

- **Флаг в `.env`.** По умолчанию `false`, и кнопки в меню нет вообще. Перед реальной
  кампанией так и оставьте.
- **Своё подтверждение.** Бот сначала показывает, что именно удалит, и просит нажать
  «🧹 Да, удалить всё». Это отдельная кнопка, не общая «Отправить» от рассылок: случайный
  тап по старому подтверждению рассылки данные не снесёт.

## Оформление сообщений

Экраны служителя (статистика, заявки, дни кампании, подтверждения) отправляются с разметкой:
в Telegram через `parse_mode=HTML`, в MAX через `format=html`. Используется узкий набор тегов
(`b`, `i`, `code`) плюс эмодзи-метки — моноширинных таблиц нет намеренно, они разъезжаются
на узком экране телефона.

Всё, что пришло от людей — имена, вопросы, названия районов, текст объявления, — обязано
проходить через `esc()` из [src/core/html.ts](src/core/html.ts). Иначе одна угловая скобка
в сообщении участника ломает отправку. Забыть про это легко, поэтому на экранирование есть тесты.

Сообщения участникам (анкета и ежедневная рассылка) отправляются **без разметки**. Так сделано
осознанно: материал дня набирает служитель, и случайный символ `<` в тексте иначе обрушил бы
рассылку сразу всем. Если понадобится жирный шрифт в материалах дня, это отдельная задача
с проверкой текста перед отправкой.

## Как поменять тексты

Формулировки лежат в одном файле: [src/core/texts.ts](src/core/texts.ts).

То, что церковь меняет под себя, вынесено в `.env` и не требует правки кода:

- `CAMPAIGN_TITLE` — название кампании в приветствии
- `CHURCH_BRANCHES` — список филиалов МБВ в вопросе про церковь (через точку с запятой)
- `KIT_DATE` — когда выдают наборы
- `MDG_DEADLINE` — до какой даты координатор связывается по домашним группам
- `REPLY_TIME` — за какой срок служитель отвечает на вопрос
- `POLICY_URL`, `POLICY_TERMS_URL` — документы об обработке персональных данных

## Подключение MAX

Токен MAX выдают только верифицированному профилю организации, ИП или самозанятого на
[dev.max.ru](https://dev.max.ru) — физическим лицам и нерезидентам РФ доступ закрыт.
Верификация занимает до 48 часов по рабочим дням, модерация карточки бота ещё до 48 часов.

Порядок:

1. Зарегистрировать и верифицировать профиль организации на dev.max.ru (нужен ИНН и подтверждение руководителем).
2. Создать бота, дождаться статуса «Готов к публикации», получить токен.
3. В `.env`: `BOT_TOKEN_MAX=<токен>`, `ENABLED_PLATFORMS=telegram,max`, добавить `ADMIN_IDS_MAX`
   (узнать id: написать боту в MAX `/whoami`).
4. `docker compose up -d`

В логах при старте появится строка `MAX: бот подключён` с именем бота. Если её нет, бот не запустился:
смотрите ошибку рядом.

После подключения стоит пройти вручную **личным сообщением боту**: приветствие, кнопку
«Поделиться номером», все ветки анкеты, кнопки меню, `/export` (файл должен прийти как `.csv`).

**Не проверяйте бота в групповом чате.** Ни один адаптер не различает тип чата, поэтому в группе
пойдёт та же анкета — и телефон с ФИО увидят все участники. Регистрация задумана как личный
разговор; для групп нужен отдельный запрет (пока не сделан).

Отдельно проверить разметку: набор HTML-тегов у MAX может отличаться от Telegram. Если экраны
служителя придут с видимыми тегами или отправка начнёт падать, набор в
[src/core/html.ts](src/core/html.ts) нужно сузить до того, что MAX понимает.

## Перенос на сервер

Подойдёт обычный VPS в России: домен, TLS и белый IP не нужны, бот сам опрашивает серверы
Telegram и MAX (long polling). Нужен только исходящий доступ к `api.telegram.org` и `platform-api.max.ru` (адрес API MAX задаётся
`MAX_API_URL`; прежний `platform-api2.max.ru` из документации SDK не отвечает).

### Если Telegram недоступен с сервера

На российских хостингах `api.telegram.org` часто недоступен: DNS отдаёт адрес, который молча
таймаутит. Проверить:

```bash
curl -s -o /dev/null -m 8 -w "%{http_code}\n" https://api.telegram.org
```

`000` означает, что соединение не установилось. Лечится тем, что имя хоста прибивается
к живому IP — это уже настроено в `docker-compose.yml` через `TELEGRAM_API_IP`.
Найти рабочий адрес, если текущий перестал отвечать:

```bash
for ip in 149.154.167.220 149.154.166.110 149.154.166.120 149.154.175.50 91.108.56.130; do
  curl -s -o /dev/null -m 8 --resolve api.telegram.org:443:$ip https://api.telegram.org -w "$ip -> %{http_code}\n"
done
```

Рабочий тот, что отвечает не `000`. Его прописать в `TELEGRAM_API_IP` в `.env` и перезапустить
бота. Имя домена при этом не подменяется, поэтому TLS и проверка сертификата остаются настоящими.

Признак того, что адрес перестал работать: при старте в логе нет строки `Telegram: бот подключён`,
а вместо неё ошибка про `getMe`. MAX (`platform-api.max.ru`) с российских хостингов доступен
и в таком обходе не нуждается.

| Вариант | vCPU | RAM | Диск | Для чего |
| --- | --- | --- | --- | --- |
| Минимум | 1 | 1 ГБ | 10 ГБ SSD | до ~1–2 тыс. участников |
| Рекомендуемый | 2 | 2 ГБ | 20 ГБ SSD | запас до ~10 тыс., сборка образа на сервере |

Расход памяти: Node около 150–250 МБ, Postgres 200–400 МБ, остальное на систему. Данные занимают
единицы мегабайт даже на десять тысяч анкет. Рассылка двум тысячам участников при `BROADCAST_RATE=20`
занимает около двух минут на платформу.

Порядок переноса:

```bash
# на сервере
git clone <репозиторий> /opt/church40bot && cd /opt/church40bot
# скопировать .env с ноутбука (в git его нет)
docker compose up -d --build
```

Если на ноутбуке уже есть участники, перенести базу:

```bash
# на ноутбуке
docker compose exec -T db pg_dump -Fc -U church church40 > church40.dump
# на сервере
docker compose exec -T db pg_restore -U church -d church40 --clean --if-exists < church40.dump
```

### Автодеплой из GitHub Actions

Разовый перенос выше нужен только один раз — дальше `.github/workflows/ci.yml` сам
выкладывает каждый мерж в `main`: на PR гоняет `typecheck` + тесты (с Postgres-сервисом) +
сборку образа, а после мержа по SSH заходит на сервер, подтягивает код (`git pull`, каталог
на сервере — git-репозиторий) и вызывает `scripts/deploy.sh`. Тот поднимает `bot`, дожидается
в его логе строки «схема базы актуальна» (значит, миграции применены) и только тогда поднимает
`dashboard`. Бэкап больше не шаг деплоя: это отдельный systemd-таймер (см. «Бэкапы»), который
`deploy.sh` переустанавливает при каждой выкладке.

Нужны пять секретов репозитория (Settings → Secrets and variables → Actions):
`SSH_DEPLOY_KEY` (приватный ключ отдельной пары, не личный), `SSH_HOST_IP`,
`SSH_HOST_PORT`, `SSH_USER`, `SSH_DEPLOY_PATH` (путь вида `/opt/church40bot` — тот,
куда сделан `git clone` выше). Публичная половина ключа должна лежать в
`~/.ssh/authorized_keys` пользователя `SSH_USER` на сервере.

**`.env` и `backups/` в git нет** и деплоем не затрагиваются: боевой `.env` живёт только на
сервере, копировать его между ноутбуком и сервером вслепую нельзя (перезапишет боевые токены
и пароли). Новая обязательная переменная в коде требует дописать её в серверный `.env` **до**
мержа: иначе сервис после деплоя не стартует.

Чтобы красный CI реально блокировал мерж, а не просто светил крестиком, в Settings →
Branches → правило для `main` нужно включить Require status checks to pass и выбрать
джобу `test`.

## Дашборд домашних групп

Отдельный сервис `dashboard` из того же образа: `node dist/dashboard/index.js`. Отдаёт
`dashboard/home-groups.html` за паролем. Порт публикуется только на `127.0.0.1:8090` по
умолчанию; чтобы открыть его снаружи по домену и TLS, нужен nginx (или другой reverse
proxy) на хосте. **Пока своего домена нет** — сайт открывают по голому `http://<ip>:8090`
(сейчас это `http://5.23.48.25:8090/groups`): для этого `DASHBOARD_BIND=0.0.0.0` в `.env`
(публикует порт наружу вместо `127.0.0.1`) и обязательно `DASHBOARD_COOKIE_SECURE=false`
рядом — иначе браузер не отправит куку сессии обратно по незашифрованному http, и вход
не сохранится.

**Разделы** (порядок как в шапке): Аналитика, Регистрация, Заявки, Домашние группы,
40 дней, Участники (координаторы), Добавить. Подробное описание для служителей —
[КАК-РАБОТАЕТ-ДАШБОРД.md](КАК-РАБОТАЕТ-ДАШБОРД.md).

- **Заявки** — таблица с двумя рядами фильтров (статус и вид заявки: ведущие, состоят,
  готовы открыть, дают дом, ищут группу, без заявки), фильтры по ответственному и по группе;
  в раскрытой строке меняются статус, группа и ответственный.
### Включение новых вопросов анкеты

Вопросы про удобное время и адрес включаются настройкой `EXTRA_QUESTIONS` в `.env`:
`off` (по умолчанию) — никому, `all` — всем, список id (`111111111` или `max:111111111`) —
только этим людям. Так их сначала проверяют на себе в рабочем боте. Подробно, с шагами для
владельца сервиса, — в [docs/ВЫКЛАДКА-И-ПРОВЕРКА.md](docs/ВЫКЛАДКА-И-ПРОВЕРКА.md).

### Досылка вопросов тем, кто уже зарегистрирован

Большинство людей анкету уже прошли. Им приглашение отправляет служитель: кнопкой **«📝 Дослать вопросы»** в боте
(команда `/extra`) или кнопкой «Отправить доп. вопросы» в «Настройки → Бот: новые вопросы анкеты» нового интерфейса
(полный вход, не нужно быть служителем бота; правила получателей общие: `src/core/extraInvites.ts`, сервис пишет тем же
`BroadcastSender`, а подтверждается конкретное число получателей). Бот показывает, сколько человек получат приглашение, и после подтверждения
пишет каждому одно сообщение с кнопками «Ответить» и «Не сейчас». Нажавшему «Ответить» бот задаёт
те же два вопроса (без «необязательно» и без «Пропустить»: человек уже согласился), говорит
«Спасибо», и ответы ложатся в его существующую заявку — в дашборде они видны сами. Новой
регистрации и новой заявки при этом не создаётся. На ответ даётся **сутки** после нажатия «Ответить»: сообщение, пришедшее позже, не записывается как ответ (бот подсказывает нажать «Ответить» ещё раз; кнопка в старом приглашении продолжает работать).

Получают приглашение только те, у кого ответ про группу «хочу присоединиться», «готов открыть» или
«дам дом», кто не заблокировал бота, ещё не отвечал на эти вопросы и не получал приглашение (каждому
оно приходит один раз, напоминаний нет), и только те, кому вопросы включены настройкой
`EXTRA_QUESTIONS` (пока в ней список проверяющих, приглашения получат только они). Тексты приглашений
— `followUpInviteJoin` и `followUpInviteLead` в `src/core/texts.ts`.

### Подбор группы

Правила автора сервиса — чистая функция `src/core/matching.ts` без базы и внешних сервисов.
В старый дашборд (`dashboard/home-groups.html`) они не подключены: подбор показывает новый
интерфейс (в разработке, см. `docs/`).

Жёсткие условия — группа отсекается, если не выполнено хотя бы одно: статус «Функционирует»
или «Кампания»; «Приём новых» не «Нет»; возраст группы пересекается с возрастом человека;
у группы не стоит отметка «Не направлять» (колонка `groups.do_not_refer`: она скрывает группу
из подбора, в реестре группа остаётся; поставить её пока можно только в базе). Если возраст человека или группы неизвестен («любой», пусто), по возрасту
группа не отсекается.

Очки: тот же район +3; то же метро или ориентир +2; «Кампания» в период кампании +2;
участников меньше, чем в среднем по соседним группам района, +1. Район и метро берутся из
свободного текста, который человек написал в боте. Расстояния не считаем: «ближе» значит
только совпадение района и метро.

Сначала идут новые группы (статус «Кампания»); действующие добавляются, только если новых
подходящих меньше трёх. Показываем не больше пяти. При равных очках выше группа поменьше.
Бот человеку о подобранной группе не сообщает: подбор виден только служителю.

Разовое распределение сразу для всех желающих делает `src/core/distribution.ts`: люди идут по
очереди, у выбранной группы становится на одного участника больше, поэтому желающие одного района не
складываются в одну группу. Те, кто хочет открыть группу, считаются будущими новыми группами и идут
первыми, но человеку такая группа предлагается, только если совпал район или метро. К каждому
назначению пишется принцип (очки и причины) и до трёх альтернатив; назначения без совпадения по
району и метро помечаются «нужна проверка». Выгрузка в Excel и блок подсказок в карточке заявки были
сделаны для старого дашборда и убраны из ветки (остались в истории git, коммит «Подбор групп по
правилам автора сервиса» и следующие); они вернутся в новом интерфейсе.

- **Регистрация** — форма и список участников (колонки «Возраст», «Место», «Выдан набор»,
  сортировка по любому столбцу, QR и печатная карточка).
- **Домашние группы** — см. «Домашние группы и ведущие» выше.
- **40 дней** — статистика кампании: регистрации, выданные наборы, рассылки.
- **Аналитика** — графики по группам и заявкам.

После «Сохранить» страница перезагружается (данные вшиваются в неё на сервере), но
вкладка, фильтры, сортировка, прокрутка и раскрытые заявки сохраняются (`sessionStorage`).

**Темы оформления**: тёмная (по умолчанию), светлая и серая; переключатель в шапке, выбор
хранится в браузере (`localStorage`). Все цвета берутся из переменных палитры в начале
`home-groups.html`, поэтому новая тема — это новый блок переменных.

**Два входа и право удаления.** Вход по логину и паролю:

| Логин | Пароль | Права |
| --- | --- | --- |
| `mbv_admin` | `DASHBOARD_PASSWORD` | всё, **кроме удаления** |
| `super_mbv_admin` | `DASHBOARD_SUPER_PASSWORD` | всё, включая удаление групп, заявок, координаторов и регистраций |

Удаление запрещено на сервере (ответ 403 на `/group/delete`, `/request/delete`,
`/coordinator/delete`, `/leader/delete`, `/delete`), а у обычного входа кнопки ещё и скрыты.
Роль хранится в сессии; сессии, выданные до появления ролей, считаются обычными. Логины можно
переопределить `DASHBOARD_LOGIN` и `DASHBOARD_SUPER_LOGIN`.

| Переменная | Смысл |
| --- | --- |
| `DASHBOARD_PASSWORD` | пароль обычного входа, не короче 8 символов (без него сервис не стартует) |
| `DASHBOARD_SUPER_PASSWORD` | пароль полного входа, не равен обычному (без него сервис не стартует: иначе обычный вход получил бы право удалять) |
| `DASHBOARD_PORT` | порт внутри контейнера, по умолчанию 8090 |
| `DASHBOARD_SESSION_DAYS` | сколько живёт сессия, по умолчанию 30 дней |
| `DASHBOARD_COOKIE_SECURE` | `false` только при отладке или при входе по голому http |
| `REDIS_URL` | где держать сессии |
| `DASHBOARD_URL` | адрес дашборда — общая с ботом переменная: бот вставляет её в уведомления о заявках, дашборд — в ссылку «Открыть заявку», когда сам уведомляет о заявке, заведённой в нём же |

**Сессии лежат в собственном Valkey** (сервис `valkey` в `docker-compose.yml`, том
`valkeydata` — переживает перезапуск контейнера). Ни с каким соседним стеком не делится,
порт наружу не публикуется.

Что защищает вход: пароли сверяются `timingSafeEqual`, после 5 промахов с одного адреса вход
блокируется на 15 минут, кука `hg_sid` — `HttpOnly` + `Secure` + `SameSite=Lax`, выход только
POST-ом (чтобы чужая страница не разлогинивала картинкой). Страница закрыта от индексации и от
встраивания во фрейм.

**Два приложения на одном сервисе.** «Домашние группы» (`/groups`) и «Регистрация»
(`/registration`) отдаёт один и тот же процесс на одном порту — это разные пути монтирования,
а не разные сервисы. У каждого своя кука (путь равен своему префиксу), поэтому вход общий,
но не переносится автоматически со страницы на страницу. Сервис сам разбирает префикс
`/groups` или `/registration` из пути; за nginx оба `location` ведут на один upstream
(`127.0.0.1:8090`) **без обрезания префикса**.

**Обновить страницу:** файл `dashboard/home-groups.html` вшит в образ, поэтому правка попадает
на сервер деплоем (мерж в `main`) или `docker compose up -d --build dashboard`. Как пересобрать
данные из таблицы, написано в `dashboard/README.md`.

Кнопка «Выйти» в шапке добавляется на отдаче, в самом файле её нет: дашборд должен оставаться
самодостаточным и открываться прямо из файла, без сервера.

## Новый интерфейс «Домашние группы» (в разработке)

Это новая версия страницы администрирования, которая со временем заменит старый дашборд.
Она работает **рядом** со старым, а не вместо него: старый дашборд не менялся и открывается,
как раньше. Пока новый интерфейс в разработке, пользоваться служителям по-прежнему нужно старым.

Устройство: отдельный контейнер `home-groups` (тот же образ, что у бота, другая команда:
`node dist/home-groups/index.js`). Он отдаёт и интерфейс (React, собирается из `web/home-groups/`),
и данные для него. База, Valkey (хранилище сессий) и пароли общие со старым дашбордом.

| | Старый дашборд | Новый интерфейс |
|---|---|---|
| Контейнер | `dashboard` | `home-groups` |
| Порт на сервере | 8090 | 8092 |
| Адрес | `/groups` | корень сайта (`/`) |
| Кука входа | прежняя | новая, `mbv_sid` |

**Вход прежний:** те же логин и пароль, что у старого дашборда (`mbv_admin` и `DASHBOARD_PASSWORD`,
полный вход `super_mbv_admin` и `DASHBOARD_SUPER_PASSWORD`). Новых паролей заводить не нужно. Кука
другая, поэтому зайти придётся заново, но выход из одного интерфейса другой не затрагивает.

**Переменные окружения** в `.env` (все необязательные, без них работают значения по умолчанию, так что
на старте сервиса ничего дописывать не нужно):

- `HG_PORT` — порт на сервере, по умолчанию `8092`. Внутри контейнера порт всегда 8092, меняется
  только тот, по которому вы заходите снаружи. Адрес публикации задаёт `DASHBOARD_BIND`, как у старого
  дашборда: по умолчанию только `127.0.0.1`, а для доступа снаружи нужен nginx с TLS (если открыть
  порт напрямую по http, нужен ещё `DASHBOARD_COOKIE_SECURE=false`).
- `HG_PUBLIC_URL`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM` — отправка писем со ссылками на пароль (см. «Личные входы»); все необязательные.
- `HG_AUTOMATCH_SECONDS` — как часто проверять новые заявки, если включён автоматический подбор (секунды, по умолчанию `120`, не меньше `30`).
- `HG_DEFAULT_CAPACITY` — сколько человек вмещает группа, если число мест не указано, по умолчанию `10`.
- `YANDEX_GEOCODER_KEY` — ключ Яндекс.Геокодера. Его можно ввести и без доступа к серверу: «Настройки → Геокодер» (сохранённый ключ шифруется
  тем же `SETTINGS_SECRET`, что и ключ помощника, и важнее `.env`). Адреса групп и людей переводятся в координаты (раз в 5 минут, не больше 50 новых
  за заход, с паузой в секунду и не больше 900 запросов в сутки — бесплатный ключ даёт тысячу), результат лежит в `geocode_cache`. Подбор тогда сравнивает расстояние (до 500 м — «рядом», дальше
  доля падает, за 6 км — ноль); без ключа или для ненайденных адресов — название улицы или метро, как раньше. Адреса уходят в Яндекс. Геокодируются адреса групп любого статуса, кроме «Закрыта» (в том числе «Кампания» и «Недвижимость»), и адреса всех людей, где он заполнен (анкета, улица из заявок); район и метро — нет. Очередь идёт так: группы, открытые заявки «в группу», остальные заявки, регистрации. Что уже найдено, видно в «Настройки → Геокодер» (сводка и список ненайденных), в карточке группы и в «Параметрах подбора» заявки. Уже предложенные группы сами не пересчитываются: после дозаполнения координат нажмите в «Заявках» «Пересчитать все предложения».
- `HG_WEB_DIR` — где лежит собранный интерфейс. В контейнере это `/app/web-dist`, задавать самому не надо.

### «Предварительно» и «Утвердить»

Главное правило: **предложение — это только предложение.** Расчёт сервиса (позже — языковая
модель) предлагает группу, но человек считается распределённым лишь после того, как координатор
нажал «Утвердить» на этой заявке. Массовых кнопок «утвердить всё» нет.

На карточке заявки четыре действия (`POST /api/v1/requests/:id/…`, тело — JSON):

| Действие | Что происходит |
|---|---|
| **Утвердить** (`approve`) | заявка становится «Исполнена», привязывается к группе (`group_id`, `final_group`), снимается «нужен звонок». Нет мест — сервер переспрашивает (`group_full`), повтор с `force` утверждает всё равно. В группу «Не направлять», закрытую или архивную утвердить нельзя вообще |
| **Другая группа** | то же `approve`, но с группой, выбранной вручную |
| **Отклонить** (`reject`) | заявка остаётся открытой, группа запоминается как отклонённая и этой заявке больше не предлагается; причина из списка, для «Другое» нужен комментарий |
| **Нужен звонок** (`need-call`) | отметка `requests.callback`: заявка уходит в «Перезвонить» (даже если плана нет), пока человека не утвердят |

Всё это — в одной транзакции с записью в `audit_log` (кто, когда, что было → стало), а заявка на
время действия блокируется: двое координаторов, нажавших одновременно, утвердят её только один раз.
Записи журнала видны в ленте карточки. Личных данных (ФИО, телефоны) в журнал не пишутся.

Таблица `placement_proposals` («предварительно») хранит предложения и решения: источник
(`script` — расчёт, `agent` — языковая модель, `manual` — выбрал координатор), статус
(`proposed` → `approved` / `rejected` / `superseded`), причину отказа. На заявку одно действующее
предложение. Расчёт сервиса в таблицу не пишется (он пересчитывается на каждый показ): туда
попадает уже решение координатора.

Миграция `021` только добавляет таблицы и колонку `requests.callback`. Старый дашборд и бот её не
замечают. Вход пока общий, поэтому автор в журнале — логин входа (`mbv_admin` или `super_mbv_admin`).

### Создание записей, параметры подбора, «пульт»

- **«+ Создать»** (шапка): «Заявка» и «Группа» создаются в самом интерфейсе (`POST /api/v1/requests/create`,
  `/groups/create`, тело `{fields: {…}}`). Проверки — **те же функции**, что у форм старого дашборда
  (`src/dashboard/forms.ts`), поэтому правила ввода одни на оба интерфейса; созданное помечается
  `source='ui'` (повторный перенос таблицы его не затрёт) и пишется в журнал. Справочники для форм
  (районы, статусы, форматы, возрастные категории, координаторы) отдаёт сервер: `GET /api/v1/form-meta`.
  **«Участник (регистрация)»** тоже в новом интерфейсе (`POST /api/v1/people/create`, форма — те же функции
  разбора, что у `/registration` старого дашборда). Ответ про Малую группу заводит заявку (`origin='ui'`),
  как и у бота. Печатная карточка с QR: `GET /api/v1/people/:id/card`, сам QR — `/people/:id/qr`, эмблема —
  `/api/v1/assets/church-logo.png` (всё за входом; папка эмблемы — необязательная `HG_ASSETS_DIR`,
  по умолчанию `/app/dashboard/assets`). В журнал пишется номер регистрации, без ФИО и телефона.
- **Уведомления служителям.** Заявка, заведённая в новом интерфейсе (через «Создать» или регистрацию),
  уходит служителям в Telegram/MAX тем же `AdminNotifier`, что и заявка из бота: общий сборщик
  `src/admin/notifierFromEnv.ts` используется и старым дашбордом, и этим сервисом (токены и `ADMIN_IDS_*`
  те же, опрос платформ не запускается). Если задан `HG_PUBLIC_URL` (теперь его читает и бот), ссылка в
  сообщении ведёт на заявку в новом интерфейсе, иначе — в старый дашборд.
- **Разбор «других обращений» по справочникам** (`src/home-groups/reconcile/`). «Уже состою в группе» ищет группу по
  имени ведущего из анкеты, «уже веду группу» — по имени и телефону самого человека (`match.ts`: слова имени без
  регистра, «ё/е», в любом порядке; слово совпадает с формой того же слова, длины отличаются не больше чем на букву, так
  что «Иван» и «Иванов» — разные; телефон — последние десять цифр). Совпадение точное (`exact`, предлагается к
  подтверждению) или вероятное (`likely`, фамилия и инициал: выбирает человек). Номер ведущего даёт `exact`, только если
  в имени человека есть слово ведущего (жена с телефоном мужа); чужое имя с общим номером — `likely`. Результат —
  `OtherItem.reconcile` (`ready` / `choose` / `none` / `noleader` / `nouser`) и `OtherItem.gist` (суть одной фразой).
  В карточке у блоков «Разбор» и «Работа с заявкой» ключи React свои (`reconcile-<id>`, `work-<id>`): общий `key={id}`
  у соседей оставлял в карточке блоки прежнего обращения, и кнопка в них действовала на то обращение; тест —
  `Others.spec.tsx` («при переходе к другому обращению…»).
  Применение — `POST /api/v1/requests/:id/reconcile {groupIds}` (одна или несколько групп, до 20; прежнее `{groupId}`
  принимается; `PlacementRepo.reconcile`, одна транзакция + запись `request.reconcile` в журнал без имён, в `after`
  `group_id` — первая группа, `group_ids` — все): «уже состою» — строка в `group_members` со ссылкой на `users` в каждую
  группу, «уже веду» — `groups.leader_user_id` у каждой (миграция `030`; чужую связь не перезаписывает, ответ `conflict`;
  группа из таблицы переходит в `source='ui'`). Все или ничего: недоступная группа или чужой ведущий у любой отменяют
  разбор целиком. В интерфейсе группы отмечаются галочками (найденные) и через «Другие группы…» (из справочника). Обращение закрывается как «Исполнена». `POST /api/v1/requests/reconcile-ready {ids}`
  заново считает группу на сервере для каждого обращения и применяет только однозначные (клиент группу не называет).
  Вид разбора выводится из типа обращения; «хочу открыть» и вопросы не разбираются. Группа связана с ведущим — это
  `GroupItem.leaderKey` («u12»).
- **«Подобрать заново».** Закреплённое предложение хранит отпечаток данных заявки (район, возраст, дни,
  время, улица; миграция `026`). Изменились данные — предложение помечается «Данные изменились», не
  закрепляется и пересчитывается при следующем подборе. Кнопка в карточке заявки
  (`POST /api/v1/requests/:id/rematch`) сбрасывает закрепление одной заявки, «Пересчитать все предложения»
  (`POST /api/v1/matching/rerun-all`) — всех открытых; группы, которые координатор отклонил, и уже
  утверждённые заявки не трогаются.
- **Рабочее место координатора** (карточка заявки). «Позвонить» (`tel:`), «Написать» (`sms:`) и «Скопировать
  номер»; «В работе у» (`POST /api/v1/requests/:id/assign`, поле `requests.responsible`); «Итог звонка»
  (`/call`: дозвонился, не дозвонился, просил позже, отказался; «не дозвонился» и «позже» оставляют заявку
  в «Перезвонить», остальные снимают отметку); «Править данные» (`/edit`: ФИО, телефон, возраст, район,
  комментарий). Правка района и возраста меняет отпечаток данных, и закреплённое предложение само помечается
  «Данные изменились». Все три действия — только для открытых заявок, пишутся в ленту; в журнал идут названия
  изменённых полей, без телефона и имени. На экране «Заявки» есть фильтр «В работе у» (параметр `resp`) и
  «Мои виды» — сохранённые наборы фильтров в `localStorage` браузера (поиск по имени в вид не попадает без
  явной галочки). В «Справочнике» остаются его прежние «Сохранённые виды».
- **Рабочее место руководителя.** Сводка «Команда» (`GET /api/v1/team`): сколько заявок открыто и у кого, как давно
  они ждут (0–2, 3–7, 8–14, 15+ дней), заявки «без движения» дольше недели, действия за 7 дней по логинам
  (пока вход общий, все действия идут под одним именем, по-настоящему разведёт личный вход).
  Массовые действия над заявками (`POST /requests/bulk`, до 100 за раз): передать координатору или поставить
  «нужен звонок». Правка группы и координатора (`/groups/:id/update`, `/coordinators/:id/update`, создание
  координатора `/coordinators/create`): правка частичная, адрес и телефоны группы новый интерфейс не отдаёт и
  не затирает. Переименование координатора переписывает его имя в «в работе у» и в группах. Удаление групп,
  координаторов и заявок (`…/delete`) и выгрузка в CSV (`/export/requests.csv`, `/export/people.csv`, с телефонами)
  доступны только полному входу; удаление мягкое (запись скрывается), каждая выгрузка пишется в журнал. В CSV
  значения, похожие на формулу (`= + - @`), экранируются.
- **Закрытие и возврат заявки, прочие обращения.** `POST /api/v1/requests/:id/close` (обработано или
  аннулировать с причиной из списка `CANCEL_REASONS`) и `/reopen` (вернуть утверждённую или закрытую заявку в
  «В работе», группа и причина очищаются). В `GET /requests` поле `others` — всё, что не идёт в подбор: «хочет
  открыть группу или дать дом», вопросы, «уже состоит» и аннулированные «хочу в группу» (закрытых не больше 200).
  Тип `join_group` — единственный, для которого строится подбор.
- **Кампания и регистрация на месте.** `GET /api/v1/campaign` — та же статистика, что раньше показывал старый
  дашборд (`src/dashboard/campaignStats.ts`). Страница `/registration` отдаёт тот же интерфейс после входа (вход
  с возвратом, `?next=/registration`), а интерфейс по пути показывает только форму регистрации.
  `POST /people/:id/delete` (только полный вход) стирает регистрацию вместе с заявками и рассылками.
- **Настройка бота «новые вопросы анкеты».** Хранится в `app_settings` (`bot.extra_questions`: `off`, `all` или
  список id), меняется в «Настройки → Бот: новые вопросы анкеты». Бот читает её раз в 15 секунд
  (`src/core/rollout.ts`); пока её не меняли, действует `EXTRA_QUESTIONS` из `.env`. При недоступной базе бот
  остаётся на значении из `.env`.
- **Старый дашборд отключается** строкой `LEGACY_DASHBOARD=off` в `.env` (см. `docs/ПЕРЕХОД-НА-НОВЫЙ-ИНТЕРФЕЙС.md`):
  сервис вынесен в профиль compose `legacy`, `scripts/deploy.sh` по этому значению поднимает или останавливает его.
  Ссылки бота «в дашборд» ведут на `HG_PUBLIC_URL`, если он задан.
- **Помощник по разбору заявок** (DeepSeek, `src/home-groups/assistant/`, клиент `src/platform/llm/deepseek.js`).
  Подключается в «Настройки → Помощник» (только полный вход): провайдер (DeepSeek, OpenAI, OpenRouter, другой по https), модель и
  ключ. Ключ хранится в `app_settings` зашифрованным (`src/platform/settings/secrets.ts`, AES-256-GCM; секрет шифрования —
  `SETTINGS_SECRET`, а без него `DASHBOARD_SUPER_PASSWORD`; при смене секрета ключ вводят заново), в интерфейс не возвращается
  (только последние четыре символа). Кнопка «Проверить» (`POST /settings/assistant/llm-test`) делает один запрос и показывает
  код ответа и пояснение провайдера с закрытыми ключами. Клиент читает подключение при каждом обращении (`llmConfig.ts`,
  `LlmSource`), перезапуск не нужен; пока в настройках пусто, действуют `DEEPSEEK_API_KEY`/`DEEPSEEK_MODEL`/`DEEPSEEK_BASE_URL`
  из `.env` (см. `docs/ПОДКЛЮЧЕНИЕ-ПОМОЩНИКА.md`). Переключатель «Помощник включён» в тех же настройках (по умолчанию выключен). Читает записи, которые скрипт не понял (район, возраст, удобное
  время), и подсказывает вопросы для разговора; **группу не выбирает**: разбор (`request_hints`, миграция `027`)
  подставляется в расчёт, а группу находит тот же подбор. К модели уходят только возрастная категория, место и
  удобное время, очищенные от телефонов, почт и ссылок, — и лишь то, чего скрипт не понял (`needs`); рядом идёт то, что
  скрипт уже определил (`script`: район, дни недели, время суток, «кроме…»): дни разобраны кодом, заново модель их не
  разбирает, а её ответ по уже понятому отбрасывается. Имён, адресов и данных групп у неё нет. Ответ модели
  перепроверяется по справочникам (район только из списка, возраст только из категорий), в журнале — числа и название
  модели. Если запись изменили, разбор перестаёт применяться. За запуск — не больше 40 заявок, по 20 в запросе.
  Инструкции (роль, принципы, шаги, примеры) правятся в «Настройки → Инструкции агентов».
- **Чат помощника «✦ Помощник»** (вопросы по базе: «где перебор групп?», «кто ведёт несколько групп?»; только чтение,
  `src/home-groups/assistant/chat.ts`). Модель сама пишет запросы, но выполняются они **от роли `assistant_ro`**
  (`SET LOCAL ROLE`, транзакция только для чтения, таймаут 8 с, до 100 строк, один оператор SELECT) и только к
  представлениям схемы `assistant` (`migrations/029`): таблиц, имён, телефонов, заметок и служебных данных там нет.
  **Имён модель не видит:** у людей постоянные условные номера (Участник-1042, Заявитель-77, Человек-5,
  Ведущий-3fa9c1, Координатор-b21e07; один человек всегда с одним номером), телефоны замаскированы (видны две цифры),
  дубли ищутся по необратимому «ключу телефона». Имя в вопросе служителя заменяется номером до отправки, а в ответе и
  таблице номера обратно превращаются в имена на сервере (`pseudonyms.ts`) — их видит только служитель. Ограничения:
  20 вопросов за 10 минут с одного входа, 300 в сутки, не более 5 обращений к базе на вопрос. В журнал идут число
  запросов и строк, без текста вопроса и ответа. Нужна роль `assistant_ro` (миграция создаёт её, если у пользователя
  базы есть право создавать роли; иначе чат недоступен, остальное работает).
- **Улица и удобное время** (карандаш в карточке заявки; `POST /api/v1/requests/:id/params`): ответ человека
  из анкеты (`users.address_raw`, `users.schedule_raw`) не затирается — правка координатора лежит рядом
  (`requests.manual_street`, `manual_schedule`, миграция `025`) и имеет приоритет; пустое значение убирает
  правку. Свободный текст разбирается честно (`parseHumanSchedule`): «пн, ср — с 17 до 22 часов» → Пн, Ср,
  вечер; «вторник утром или вечером» → Вт, время неизвестно.
  **Дни недели** разбирает скрипт (`src/home-groups/plan/days.ts`), а не нейросеть, и тем же разбором читается колонка
  «день» группы: сокращения (`пн, вт, ср, чт, пт, сб, вс`, `пон, четв., воскр.`), названия и падежи («в пятницу»,
  «по вторникам», «средой»), перечисления («вт и чт», «сб/вс»), диапазоны («пн-ср», «с понедельника по среду»,
  «пт-пн»), «будни», «выходные»; «пн-ср-пт» — перечисление, а не диапазон. Слова вроде «средний», «всегда», «пять»
  днём не считаются (разбор по целым словам). «Кроме воскресенья», «не по средам», «вторник не могу» уходят в
  неподходящие дни (`avoidDays`), «не утром» — в `avoidSlots`: такие группы в подбор не попадают. «Любой день» —
  ограничения нет. **Вес дня недели равен весу района** (`DISTRICT_WEIGHT` в `plan/settings.ts`, 40; время суток — 20,
  возраст — 25, улица — 15): день и время суток оцениваются по отдельности, группа без дня получает нейтральные 0,5.
  Улица человека («ул. Рылеева, 32, кв. 5») сравнивается по названию, без типа, дома и падежа (`plan/street.ts`);
  с названием улицы из адреса группы (адрес виден всем, кто вошёл в портал, и в списке «Группы»). Если адрес группы пуст,
  улица человека и его район сверяются со станцией или ориентиром группы (поле «Метро или ориентир»).
  В журнал пишется факт правки без текста улицы.
- **«Заявка как пришла»** (`RequestItem.original`): что человек заполнил сам — для сверки, правильно ли
  система поняла карточку. Заметки служителей туда не попадают. Улица из анкеты видна только в заявке.
- **Матрица «Сегодня»** (пульт): спрос и места по ячейкам «район × возраст» с перечнем заявок и групп в ячейке.
  Заявки без района собираются в строку «Район не определён», без возраста — в колонку «Возраст не указан»:
  проблему видно, а не прячут. Колонки возраста — категории анкеты бота и кампании: до 18, 18–25, 25–40, 40–55,
  55–65, 65+ (`AGE_COLUMNS` в `plan/parse.ts`). Общая цифра на стыке («25») у человека относится к нижней колонке, а
  группа «40-55» в соседнюю «25–40» не заходит. Группы кампании (`status='Кампания'`) помечены как новые (`isNew`).
- **«Предложена автоматически» / «Предварительный расчёт»:** расчёт сервиса показывается всегда, а кнопка «Предложить
  группы новым заявкам» (или автоматический режим) сохраняет его в «предварительно» (в базе — закреплённое предложение).
  Сохранённое не меняется само; поэтому после нажатия числа в «Сегодня» не растут — растёт «Предложено автоматически».
  Слово «распределено» занято за утверждёнными (плитка «Распределено 12 из 18»), поэтому для предложений оно не используется.
  «Утверждено сегодня» считается по журналу (`request.approve`) в поясе сервиса.

### Подбор для новых заявок и счётчик участников

**Накопленные сопоставления.** Расчёт не пересчитывается заново на каждый показ: его результат
сохраняется в `placement_proposals` (источник `script`). Раз предложенная группа не меняется, пока она
остаётся доступной (не «Не направлять», не закрыта, есть место, не отклонена координатором), а новые
заявки подбираются **вокруг** уже предложенных: движок обрабатывает закреплённые предложения первыми,
поэтому новая «трудная» заявка не отнимает место у той, что уже ждёт. Если группа стала недоступна,
предложение заменяется (или снимается, если подходящей больше нет).

- **Кнопка «Подобрать для новых заявок»** на экране «Заявки» (`POST /api/v1/matching/run`) считает и
  сохраняет предложения для заявок, у которых их ещё нет. Доступна обоим входам.
- **Автоматический режим** — переключатель там же (`POST /api/v1/matching/auto`, только
  `super_mbv_admin`). Включён — сервис раз в `HG_AUTOMATCH_SECONDS` секунд (по умолчанию 120, не меньше
  30) сам подбирает новые заявки. Переключатель хранится в базе (`app_settings`, ключ `matching.auto`) и
  читается на каждом проходе, поэтому перезапуск не нужен. Первый раз запускают кнопкой, чтобы увидеть
  результат, потом включают автоматику.
- Каждый запуск пишется в журнал (`matching.run`: сколько создано, заменено, без изменений); автор
  автоматического — «авто». Заявку подбор не меняет: распределённым человек считается после «Утвердить».

**Число участников.** После «Утвердить» сервис сам добавляет утверждённых к числу участников группы:
считаются утверждения по журналу, сделанные **после даты последней обратной связи** ведущего и всё
ещё действующие (заявку не вернули в работу и не перенесли в другую группу). Ведущий сообщает число
участников — оно уже включает тех, кого утвердили до этой даты, — поэтому, когда ведущий обновит число и
дату, счётчик «утверждено после обратной связи» обнулится сам. В «Справочнике» это видно пометкой
«+N». Утверждения в день обратной связи считаются уже учтёнными. Заявки из таблицы церкви в счётчик не
входят.

Миграция `022` добавляет таблицу настроек `app_settings` (ключ → значение).

### Раздел «Настройки» (только `super_mbv_admin`)

Вкладка видна только полному входу; обычному входу API отвечает 403, а вкладки нет. Код раздела
(`src/platform/settings/`, `web/home-groups/src/features/settings/`) не знает про заявки и группы:
он рассчитан на то, чтобы потом переехать в «витрину» платформы без переделок.

| Раздел | Что показывает |
|---|---|
| **Состояние сервера** | процессор (нагрузка к числу ядер), память, диск, база (ответ, размер, подключения), хранилище входов, время работы сервиса. Общий статус — худший из метрик; тревога и «критично» заданы порогами в `health.ts` (диск: 80% и 92% занятого, память: меньше 20% и 10% свободной). Память и нагрузка — всего сервера, а не контейнера. Обновляется каждые 30 секунд |
| **Журнал ошибок** | таблица `system_errors`: сюда пишутся ошибки обработки запросов и сбои автоматического подбора. Телефоны и почты вырезаются при записи; записи старше 90 дней удаляются |
| **Журнал регистрации** | последние 200 записей `audit_log`: кто, когда, что, «было → стало» |
| **Инструкции агентов** | тексты инструкций по блокам с **версиями** (`agent_prompts`): правка — новая версия, откат — «сделать действующей» старую; старые версии не удаляются. Пока блок не правили, действует текст по умолчанию из кода (`defaults.ts`). Служебный блок (формат ответа, инструменты, границы) только показывается: его задаёт код |
| **Пользователи и роли** | личные входы (см. ниже): список людей, приглашения, сброс пароля, переключатель режима |

Сам агент (запуск, инструменты) в этот раздел не входит: здесь только хранение и правка его инструкций.
Миграция `023` добавляет `system_errors` и `agent_prompts`.

### Личные входы

Каждый служитель входит под своим логином (`p_ivanova`: первая буква имени, `_`, фамилия латиницей) и
**сам задаёт пароль** по одноразовой ссылке. Всё делается в «Настройки» → «Пользователи и роли»
(только `super_mbv_admin`).

1. **Завести человека:** ФИО, почта, роль («Обычный» — `admin`, «Полный» — `super`), логин по желанию
   (иначе подберётся сам, при совпадении — с цифрой). Человеку уходит письмо со ссылкой; пароль админ
   никогда не видит и не придумывает.
2. **Человек открывает ссылку** (`/set-password?token=…`), придумывает пароль (не короче 10 знаков, не
   только цифры, не из списка самых частых) и повторяет его. Ссылка одноразовая; приглашение живёт 7
   дней, ссылка на сброс — 2 часа. Новая ссылка гасит прежние.
3. **Сброс пароля:** кнопка «Сбросить пароль» у человека или «Забыли пароль?» на странице входа
   (`/forgot`: логин или почта; ответ всегда одинаковый, существует ли такой человек, не раскрывается;
   не больше 3 писем в час на человека и 10 запросов в час с одного адреса). После смены пароля все
   прежние входы человека закрываются.
4. **Включить личные входы** — кнопка в том же разделе, доступна, когда хотя бы один действующий
   человек уже задал пароль. После включения **общий обычный вход (`mbv_admin`) перестаёт работать**,
   в том числе для уже открытых сессий; общий полный (`super_mbv_admin`) остаётся запасным, чтобы
   никто не остался без доступа. Пока режим выключен, личные логины не принимаются, всё работает как
   раньше. Выключение возвращает общий вход.
5. **Отключение человека** закрывает его вход сразу (роль и состояние берутся из базы с кэшем на 5
   секунд, а не из сессии). Себя отключить или понизить нельзя; при включённых личных входах нельзя
   отключить последнего действующего человека.

Действия в журнале подписаны личным логином. В журнал не попадают почта, пароль, его хеш и токен.
Пароль хранится только как хеш `scrypt`, токены ссылок — как `sha256`.

**Почта.** Необязательна: пока `SMTP_HOST`, `SMTP_FROM` и `HG_PUBLIC_URL` не заданы, ссылку на пароль
админ видит на экране и передаёт сам (она одноразовая и недолгая). Адрес в письме берётся только из
`HG_PUBLIC_URL`, а не из заголовков запроса: иначе ссылку можно было бы подменить. Письма — обычный
текст, отправка по SMTP с обязательным шифрованием (`SMTP_SECURE=true` для порта 465, иначе STARTTLS).

**Чего это пока не покрывает.**
- Старый дашборд (порт 8090) по-прежнему пускает по общим логинам и паролям: личные входы
  действуют только в новом интерфейсе. Пока общие пароли известны, закрыть доступ полностью нельзя.
- Права-галочки по сервисам — отдельный этап; пока две роли.
- Почта сотрудников хранится в базе (`staff.email`) — это единственные адреса в базе; в обезличенные
  представления помощника (`docs/assistant-readonly.sql`) и в тексты для языковых моделей они не
  попадают и не должны.

Миграция `024` добавляет `staff` и `staff_tokens`. Новая зависимость — `nodemailer`.

### Выкладка и откат

Отдельных действий не требуется: `scripts/deploy.sh` поднимает сервисы по порядку **бот, дашборд,
home-groups**. Миграции накатывает только бот, поэтому остальные идут за ним. При первой выкладке образ
соберётся дольше обычного: ставятся зависимости интерфейса. Проверить, что сервис жив:

```bash
docker compose ps home-groups                       # статус должен стать healthy
docker compose logs --tail 50 home-groups
curl -s http://127.0.0.1:8092/health                # на сервере
```

Если с новым интерфейсом что-то не так, **бот и старый дашборд это не затрагивает**. Отключить его:

```bash
docker compose stop home-groups
```

Следующий деплой поднимет его снова; чтобы он не возвращался, уберите сервис из `docker-compose.yml`
(или сделайте откат коммитом через PR).

## Данные церкви в базе

Выгрузка Google-таблицы живёт в базе, а не в файле дашборда. Таблицы: `groups` (все столбцы
листа «МАЛЫЕ ГРУППЫ»), `requests` (заявки листа ЗАЯВКИ и заявки бота в одном пайплайне),
`coordinators`.

Обновление: `python3 dashboard/tools/extract.py "…xlsx" > dashboard/data.json`, затем
`npm run import:spreadsheet`. Подробности — в `dashboard/README.md`.

**Что правили в дашборде, импорт не трогает.** Правка или удаление строки переводит её из
источника «таблица» в «ui», и заново из выгрузки она не вставляется. Иначе очередной импорт
затирал бы правки и возвращал удалённое.

**Статусы заявок теперь одни для всех:** «Новая», «В ожидании», «В работе», «На контроле»,
«Исполнена», «Аннулирована». Открытой считается заявка, которую не исполнили и не аннулировали.
Раньше в базе было два машинных значения (`new`/`closed`), а в листе шесть человеческих.

**Очистка базы стала выборочной.** Кнопка «Очистить базу» убирает участников, их сессии, дни
кампании, рассылки и **только заявки бота** (`origin='бот'`). Данные церкви — группы, заявки из
выгрузки, координаторы — остаются. Иначе `TRUNCATE ... CASCADE` снёс бы заявки целиком: CASCADE
смотрит на сами связи между таблицами, а не на строки.

## Бэкапы

```bash
./scripts/backup.sh
```

Кладёт сжатый дамп в `backups/`, хранит две недели. Это отдельный systemd-таймер на сервере
(`deploy/systemd/`, раз в сутки в 03:00 UTC), запускается сам по себе, без привязки к выкладкам; `scripts/deploy.sh` переустанавливает его
юниты на каждый деплой. Автозаливки никуда нет (пробовали Google Drive через
сервис-аккаунт — упёрлись в Shared Drive как платную функцию Workspace) — актуальный
дамп забирают с сервера на свой компьютер скриптом (адрес сервера и ключ — свои
переменные окружения, репозиторий публичный, в код они не зашиты):

```bash
export CHURCH40_HOST=root@<host>
export CHURCH40_KEY=~/.ssh/<ключ>   # необязательно
./scripts/fetch-backup.sh           # или ./scripts/fetch-backup.sh ~/куда-нибудь
```

Восстановление:

```bash
docker compose exec -T db pg_restore -U church -d church40 --clean --if-exists < backups/файл.dump
```

## Как это устроено

```
src/
├── core/            общий сценарий, ничего не знает про Telegram и MAX
│   ├── platform.ts  контракт адаптера: приходящие события и способы ответить
│   ├── fsm.ts       диалог регистрации как чистая функция, покрыт тестами
│   ├── router.ts    исполняет эффекты FSM: пишет в базу, отправляет ответы
│   ├── updateQueue.ts  очередь апдейтов: люди параллельно, один человек по порядку
│   ├── texts.ts     все тексты и подписи кнопок
│   ├── groups.ts    справочники районов, статусов и форматов групп
│   └── flows/       команды служителей
├── admin/           клавиатура служителя, права, уведомления о заявках
├── adapters/        grammY для Telegram, @maxhub/max-bot-api для MAX
├── broadcast/       расчёт дня кампании, планировщик, отправка с троттлингом
├── dashboard/       HTTP-сервер дашборда, вход и роли, разбор форм
├── db/              миграции и репозитории (plain SQL, без ORM)
└── deps.ts          сборка зависимостей в одном месте
dashboard/           home-groups.html — вся страница дашборда одним файлом
migrations/          SQL-миграции, накатывает только бот при старте
deploy/systemd/      таймер ежедневного бэкапа
scripts/             deploy.sh, backup.sh, fetch-backup.sh, import-spreadsheet.mjs
```

Подробнее о стеке — [docs/TECH-STACK.md](docs/TECH-STACK.md); для разработчика и ИИ-помощника —
[CLAUDE.md](CLAUDE.md).

Четыре решения, которые стоит знать при доработке:

**Состояние диалога живёт в Postgres**, не в памяти: анкета переживает перезапуск контейнера.
Весь доступ идёт через `SessionsRepo`, так что при большой нагрузке его можно заменить на Redis,
не трогая сценарий.

**Бот рассчитан на сотню человек одновременно.** Библиотеки опроса ждут обработчик апдейта, а
значит, без очереди люди стояли бы друг за другом. `UpdateQueue` обрабатывает до 16 апдейтов
разом (пул соединений с базой — 20), а апдейты одного человека идут строго по порядку: анкета
читает и пишет его состояние целиком, и два шага одновременно перетёрли бы друг друга (двойной
тап по кнопке). Когда все места заняты, опрос притормаживает сам. Уведомления служителям уходят
в фоне и не занимают место в очереди; при остановке бот доделывает принятое.
Проверено тестом на 100 одновременных анкет (`tests/concurrentUsers.spec.ts`).

**Рассылка идемпотентна.** Таблица `deliveries` с ограничением `UNIQUE (broadcast_key, user_id)` —
источник истины. Перезапуск посреди рассылки продолжает работу, а не начинает заново; повторный
запуск того же дня никому не пришлёт второе сообщение. Заблокировавшие бота помечаются и выпадают
из следующих рассылок.

**День кампании считается по календарю Москвы**, а не по разнице в миллисекундах: иначе рассылка
на границе полуночи уезжает на сутки. Бот, поднятый в середине дня, всё равно отправит утреннюю рассылку.

## Разница платформ, которую пришлось учесть

| | Telegram | MAX |
| --- | --- | --- |
| Запрос телефона | reply-клавиатура, её нужно потом убирать | инлайн-кнопка, номер приходит визиткой VCF |
| Начало диалога | команда `/start` | отдельное событие `bot_started` |
| Клавиатуры | reply и инлайн | только инлайн (поэтому меню везде инлайновое) |
| Отправка файла | буфер с именем | из буфера имя теряется, пишем во временный файл |
| Ошибка «слишком часто» | отдаёт `retry_after` | ждём фиксированную паузу |

Ручной ввод телефона разрешён всегда: если кнопка запроса контакта где-то не сработает,
регистрация не встанет.
