# Стек технологий

Коротко о том, из чего собран проект и почему выбрано именно это.

## Язык и рантайм

- **TypeScript 5.7** в строгом режиме (`strict`, `noUncheckedIndexedAccess`,
  `noImplicitOverride`) — единственная страховка от ошибок, линтера в проекте нет.
- **Node.js 24+**, модули ESM (`"type": "module"`), сборка — обычный `tsc` в `dist/`.
- Локальная разработка — `tsx watch` (без отдельного бандлера и без hot-reload фреймворка).

## Бот

- **grammY** — клиент Telegram Bot API.
- **@maxhub/max-bot-api** — клиент мессенджера MAX.
- Обе платформы спрятаны за одним интерфейсом `Platform` (`src/core/platform.ts`):
  остальной код получает `IncomingUpdate` и отдаёт `OutAction`, не зная, откуда пришло
  сообщение. Отличия платформ (reply-клавиатуры, диплинки, формат телефона) живут только
  в адаптерах (`src/adapters/`).
- Анкета участника — чистая функция (`src/core/fsm.ts`), без обращений к базе и сети:
  это и есть основной объект юнит-тестирования.
- **qrcode** — генерация QR-кода для карточки регистрации.

## Данные

- **PostgreSQL 18** — единственное хранилище, без ORM: SQL пишется руками в
  `src/db/repos/*.repo.ts` (по репозиторию на сущность), наружу отдаются типизированные
  интерфейсы.
- Миграции — обычные `.sql`-файлы в `migrations/`, применяются по порядку имени файла
  самим ботом при старте, учёт — в таблице `schema_migrations`. Дашборд миграции не
  накатывает.
- **Redis-клиент (`redis`) поверх Valkey** — только для сессий дашборда (отдельная база
  индекс 3 в общем Valkey сайта, свой префикс ключей). Основные данные бота в Redis не
  живут.

## Дашборд администратора

- Одна самодостаточная HTML-страница (`dashboard/home-groups.html`, вёрстка + стили +
  ванильный JS в одном файле) — без фронтенд-фреймворка и без сборки. Открывается и
  напрямую из файла, и по паролю через сервис.
- Отдаётся встроенным HTTP-сервером на `node:http` (`src/dashboard/server.ts`) — без
  Express/Fastify. Данные вшиваются в страницу на сервере (`window.HG_LIVE`) при каждом
  запросе, отдельного API для чтения нет; правки уходят POST-запросами на пару
  обработчиков в том же сервере.

## Прочие библиотеки

- **zod** — валидация переменных окружения (`src/config.ts`), бот падает при старте, если
  конфигурации не хватает, а не тихо работает неправильно.
- **pino** — структурные логи в JSON.

## Тесты

- **vitest**, весь набор — `npm test`. Проект писался по TDD: сначала падающий тест.
- Тесты на базу и на HTTP-маршруты дашборда гоняются против настоящего Postgres
  (`tests/helpers/testDb.ts` поднимает отдельную базу `church40_test` и накатывает
  миграции), а не против моков — так расхождения со схемой ловятся сразу.
- Тесты на разметку дашборда читают настоящий `dashboard/home-groups.html`, а не копию:
  домен статусов и структура страницы не могут разъехаться незамеченно.

## Инфраструктура и деплой

- **Docker**, многоступенчатая сборка (`node:24-alpine`): отдельные стадии для сборки,
  прод-зависимостей и итогового образа; контейнер работает не под root.
- **docker compose** — три сервиса из одного образа: `bot` (опрос платформ, рассылки,
  накатывает миграции), `dashboard` (тот же образ, другая команда) и `db` (Postgres).
- Сборка образа идёт из локального файлового дерева на сервере (`build: .`), не из git —
  на боевом сервере нет `.git`, обновление кода — рядовым `rsync`.
- CI/CD нет: обновления заливаются и пересобираются вручную (см. `README.md`, раздел
  «Перенос на сервер»).
