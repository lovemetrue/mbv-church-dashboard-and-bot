# Архитектура платформы «МБВ-Служения»

Черновик для согласования. Код по нему не пишется, пока план не принят. Написан простыми
словами: к каждому решению — зачем оно и что мы получаем, когда сервисов станет больше.

## 1. Коротко

- Один репозиторий, **несколько сервисов, каждый в своём контейнере**, одна общая база.
- **Общая платформа** (вход, права, журнал, оформление) написана один раз и подключается
  к каждому сервису. Новый сервис («Крещение», «Шаги») — это папка с предметной логикой, а не
  новый проект с нуля.
- **Витрина (хаб)** — отдельный небольшой сервис: вход и плитки сервисов, доступных человеку.
- **Бот** остаётся отдельным процессом. Сервисы бота не вызывают: они кладут данные в базу, а бот
  сам отправляет сообщения по расписанию.
- Сейчас без HTTPS (по решению заказчика), но всё устроено так, что включить его позже можно
  **одной настройкой на входе**, не переписывая сервисы.
- Старый дашборд не трогаем, работает параллельно и отключается после обкатки нового.

## 2. Что от нас просили (сводка)

1. Новый интерфейс «чистым листом», модульный, не одним файлом, как в референсе
   (`Сегодня`, `Заявки`, `Справочник`, `Контроль`, обзвон, помощник).
2. Сервисы нарастают (домашние группы, крещение, шаги…), каждый в своём контейнере, база общая,
   потом общая витрина.
3. Личные входы служителей (логин `p_ivanova`, пароль человек задаёт сам при первом входе),
   права по сервисам с галочками, журнал действий для статистики активности координаторов.
4. Мобильная версия: на телефоне сначала «ожидаемые действия», потом карточка человека.
5. Поток бота: координатор лично пишет человеку и жмёт «Приветственное личное сообщение
   отправлено»; бот раз в два часа (10:00–18:00 по Москве, каждый день) отправляет вопросы
   про время и место только тем, кому подтвердили личный контакт.

## 3. Схема

```
 Браузер ──http──▶  [ позже: входная точка с HTTPS ]
                         │
        ┌────────────────┼──────────────────┐
        ▼                ▼                  ▼
     Витрина         «Домашние группы»   «Крещение», «Шаги»… (потом)
   (вход, плитки,    (свой API + свой    каждый по тому же шаблону
    аккаунты)         интерфейс)
        │                │                  │
        └────── общая платформа (библиотека): вход, права, журнал ──────┐
                         │                                              │
                         ▼                                              ▼
                  Postgres (одна база) ◀── Valkey (сессии)         Старый дашборд
                         ▲                                         (доживает свой срок)
                         │
                       Бот (Telegram, MAX): рассылки, анкеты, отправка по расписанию
```

## 4. Кто за что отвечает

| Часть | Что делает | Что не делает |
| --- | --- | --- |
| Сервис («Домашние группы») | своя предметная логика, свой API, свой интерфейс | не хранит пароли, не знает про чужие сервисы |
| Платформа (библиотека) | вход, сессии, проверка прав, журнал действий, общие кнопки и оформление | не содержит предметной логики |
| Витрина | страница входа, список доступных сервисов, управление аккаунтами и правами | не показывает данные сервисов |
| Бот | диалоги, рассылки, отправка по расписанию | не работает с веб-интерфейсом |
| База | единое хранилище | у сервисов нет «своих» чужих таблиц |

Правило: **сервисы друг с другом не общаются напрямую**, только через базу и платформу. Тогда
поломка одного сервиса не роняет остальные, а их можно выкладывать по отдельности.

## 5. Данные

### Два разных понятия, которые нельзя путать
- **Участники** — люди, которые заполнили анкету в боте (таблица `users`, уже есть).
- **Служители** — те, кто входит в веб-интерфейс (новая таблица `staff`). Это разные люди и
  разные таблицы; имя `users` за участниками остаётся как есть.

### Что добавляем платформе (миграции с 021)
- `staff`: логин, имя, хеш пароля, «сменить пароль при первом входе», активен ли.
- `staff_permissions`: служитель × сервис × право (см. раздел 6).
- `audit_log`: **единый журнал** (кто, когда, в каком сервисе, что сделал, над чем, что было и
  стало). Он же заменяет `request_events` из исходного промта: лента в карточке человека — это
  выборка из журнала, а статистика активности координаторов — его сводка. Одна таблица вместо двух.
- Для «Домашних групп»: вместимость группы (по умолчанию 10, редактируется), улица для подбора,
  отметка «подтверждена ведущим», параметры заявки (район, дни, время, улица), отметка
  «приветственное личное сообщение отправлено» (кто и когда).

### Как менять базу, не ломая старое
- Миграции **только добавляют** (новые поля и таблицы с безопасными значениями), ничего не
  переименовывают и не удаляют. Тогда старый дашборд и новый работают на одной базе одновременно.
- Миграции по-прежнему накатывает бот при старте. Когда сервисов станет несколько, вынесем это в
  отдельное разовое задание «migrate», которое запускается перед всеми остальными. Решение
  отложено, чтобы не усложнять сейчас; место для него в compose оставляем.

## 6. Вход и права

- **Логин**: первая буква имени, `_`, фамилия латиницей (`p_ivanova`); при совпадении добавляется
  цифра. **Пароль** человек задаёт сам при первом входе (временный пароль заводит администратор).
- **Хранение пароля**: только хеш (`scrypt` из стандартной библиотеки Node, без новых зависимостей).
- **Права — это галочки.** Атом — одно право у сервиса; для каждого сервиса набор такой:
  - `видит сервис` (иначе плитки в витрине нет);
  - `читает без личных данных` (нет телефонов и ФИО);
  - `читает с личными данными`;
  - `создаёт и меняет записи`;
  - `отправляет` (запускает действия вне сервиса, например приглашения в боте);
  - `удаляет`;
  - `администрирует сервис`.
- **Роли — готовые наборы галочек** («координатор», «регистратор», «только просмотр»): удобно
  выдать одним щелчком, потом можно поправить галочки вручную. Атом — право, а не роль: так
  человеку с несколькими сервисами выдаются разные права в каждом.
- **Экран выдачи прав** — таблица: служители в строках, сервисы группами столбцов, внутри галочки.
- **Личные данные скрываются на сервере**, а не только в интерфейсе: без права «с личными
  данными» API просто не отдаёт телефоны и ФИО.
- **Общий вход**: пока личных входов нет, новый интерфейс использует нынешний общий (`mbv_admin`
  и полный `super_mbv_admin`), как и старый дашборд.

## 7. Бот и отправка по расписанию

Поток: координатор нажимает **«Приветственное личное сообщение отправлено»** в карточке человека →
в базе отмечается «контакт подтверждён» (кто и когда, запись в журнале) → задание в боте раз в два
часа с 10:00 до 18:00 по Москве (10, 12, 14, 16, 18) выбирает подтверждённых, но ещё не
приглашённых и отправляет им приглашение с кнопками «Ответить» и «Не сейчас». Ответ и срок в сутки
уже работают в боте.

- Отправка использует то, что уже есть и проверено: `broadcasts`/`deliveries`, ограничитель частоты,
  повторные попытки. Команда `/extra` в Telegram убирается: запуск теперь у расписания.
- Выключатель `EXTRA_QUESTIONS` остаётся аварийным: `off` останавливает отправку, по умолчанию
  `all`.
- **Задел на будущее:** когда появится второй сервис, которому тоже нужно отправлять сообщения,
  вынесем «очередь исходящих» в общую таблицу. Сейчас этого делать не будем: это лишняя
  сложность без второго потребителя.

## 8. Подбор групп

- Движок — **чистая функция** без базы и сети (`src/core/matching/`), как анкета в боте: он
  легко проверяется тестами, и им пользуются сервер и (потом) выгрузки.
- За основу берём движок из референса: веса района 40, возраста 25, времени 20, улицы 15
  (в настройках, не в коде), учёт вместимости, соседние районы (справочник в данных).
  Из прежних правил сохраняем «Не направлять», «приём новых не „Нет“» и «новые группы первыми».
- План считается на сервере по запросу для всей очереди сразу, **не хранится**: он всегда
  соответствует текущим данным. Хранятся только решения людей (утвердил, отказал) и их журнал.
- Исключение — предложения языковой модели («предварительно»): это её суждение, которое нельзя
  пересчитать, поэтому оно хранится в `placement_proposals` и становится решением только после
  кнопки «Утвердить». Подробнее — `ПРОЕКТ-АГЕНТ-КООРДИНАТОР.md`.
- Возраст сопоставляется как **диапазон** (пересечение), а не по жёстким корзинам: так работают и
  категории из бота, и свободные значения из таблицы церкви.

## 9. Интерфейс

- React 18 + TypeScript + Vite, серверные данные через TanStack Query, маршруты в адресе страницы
  (состояние фильтров и открытая карточка переживают перезагрузку).
- **Общая библиотека оформления** (кнопки, таблицы, выезжающая карточка, окна, цвета, темы:
  тёмная, светлая, серая): её используют витрина и каждый сервис, поэтому они выглядят одинаково.
- **На телефоне сначала «ожидаемые действия»** (блок «Сегодня»), затем карточка человека; таблицы
  прокручиваются сами, страница горизонтально не прокручивается.
- Шрифты кладём в сборку (без Google Fonts): сервер может не достучаться до внешних сайтов.
- Все тексты в одном файле на русском; пути и адреса API строятся от одной настройки (это
  пригодится и под будущим HTTPS, и под префиксом адреса).

## 10. Структура репозитория

Сейчас всё лежит в одном пакете (`src/`, бот и старый дашборд). Не переносим работающее, чтобы
не рисковать. Новое пишем сразу по целевой раскладке, общее выносим **когда оно нужно второму
сервису** (а не заранее):

```
src/                 бот и старый дашборд (как сейчас, не трогаем)
packages/
  platform/          вход, права, журнал (серверная библиотека)
  contracts/         схемы запросов и ответов, общие для сервера и интерфейса
  ui/                оформление и общие компоненты интерфейса
services/
  home-groups/
    server/          API «Домашних групп»
    web/             интерфейс «Домашних групп»
  hub/               витрина
migrations/          общие миграции (нумерация продолжается: 021…)
```

Минимум нового при старте: `services/home-groups/` и то, что ему нужно. `packages/*` создаём по
мере надобности; код, которым пока пользуется один сервис, живёт внутри сервиса и выносится при
втором потребителе.

## 11. Развёртывание

- Один `Dockerfile` с несколькими целями, по контейнеру на сервис: `bot`, `dashboard` (старый),
  `home-groups`, позже `hub`. Общие `db` и `valkey` как сейчас.
- У каждого сервиса свой порт (старый 8090, новый, например, 8092) и страница проверки `/healthz`.
- **Без HTTPS сейчас**: куки без флага `Secure` (настройка, как в старом дашборде). Задел под
  HTTPS: входная точка (nginx или Caddy) ставится перед сервисами позже, и сервисы об этом не
  знают; для неё нужны только настраиваемый префикс адреса и признак «за прокси».
- Выкладка в том же порядке: сначала бот (миграции), потом сервисы. Каждый сервис выкладывается
  отдельно.
- Новые переменные окружения дописываются в серверный `.env` до слияния.

## 12. Этапы и «готово»

| Этап | Что | Готово, когда |
| --- | --- | --- |
| A | Контейнер `home-groups`, оболочка, «Сегодня», «Заявки», «Справочник» **только чтение** на живой базе, план подбора | открывается на телефоне и компьютере, видны реальные группы и заявки, план объясняет выбор |
| B | «Утвердить», «Отказ», обзвон, «Приветственное личное сообщение отправлено», шаблоны писем (модальное окно), задание бота | координатор проходит заявку до конца; приглашение уходит в окно 10–18; всё в журнале |
| C | «Контроль», формы создания, выгрузка CSV | паритет с чек-листом старого дашборда |
| D | Личные входы, права-галочки, экран выдачи | служитель входит под своим логином, личные данные скрыты по правам |
| E | Витрина | один вход, плитки сервисов по правам |
| F | Помощник (за флагом) | правила без внешней модели; внешняя модель только после решения владельца |
| Настройки и агент-координатор | Раздел «Настройки» (инструкции агентов с версиями, журнал ошибок, ссылки на журнал регистрации), агент второго этапа распределения, таблица «предварительно» | координатор утверждает каждое предложение; агент не может менять заявки; инструкции правятся в интерфейсе (см. `ПРОЕКТ-АГЕНТ-КООРДИНАТОР.md`) |

Этап D можно сдвигать: по просьбе заказчика важнее увидеть живой интерфейс, а личные входы — потом.

## 13. Решения и почему именно так

| Выбор | Альтернатива | Почему так |
| --- | --- | --- |
| Модульный репозиторий, контейнер на сервис, общая база | независимые «настоящие» микросервисы с отдельными базами | базы и очереди между сервисами — лишние поломки и работа для небольшой команды; общая база заказчиком уже выбрана |
| Общая библиотека платформы | у каждого сервиса свой вход и права | иначе каждый новый сервис придётся защищать заново, а журнал разойдётся |
| Права-галочки, роли как наборы | жёсткие роли | один человек часто в нескольких сервисах с разными правами |
| Один журнал для всего | отдельные журналы | одна статистика активности и одна лента в карточке |
| Сессии на сервере (Valkey) | подписанные токены | можно мгновенно отключить человека |
| Отправка через уже готовые `broadcasts`/`deliveries` | сразу строить общую очередь | работает и проверено; обобщим при втором потребителе |
| Диапазоны возраста | жёсткие корзины прототипа | в таблице церкви возраст записан как попало |

## 14. Что мы осознанно откладываем

HTTPS и входная точка, отдельное задание миграций, общая очередь исходящих, перенос бота и старого
дашборда в `packages/`, внешняя языковая модель для общего помощника (агент-координатор — отдельное решение, см. `ПРОЕКТ-АГЕНТ-КООРДИНАТОР.md`).

## 15. Открытые вопросы

1. Нужен ли отдельный сервис-витрина уже на этапе B или хватит ссылки между сервисами до этапа E?
2. Хранить ли в журнале содержимое изменений («было → стало») для всех полей или только для
   ключевых действий (утвердил, отказал, подтвердил контакт)? Для личных данных предлагается не
   хранить значения, только факт изменения.
3. Сколько времени хранить журнал (предлагается без ограничения, пока база небольшая).
