# Задача: новая веб-морда дашборда домашних групп (модульная, с планом распределения заявок)

Ты работаешь в репозитории `lovemetrue/mbv-church-dashboard-and-bot`. Прочитай `CLAUDE.md` целиком до начала работы: там язык проекта (код, комментарии, имена тестов и коммиты **на русском**), команды, архитектура и ловушки, на которые уже наступали. Не удаляй существующие комментарии, не разобравшись.

К задаче приложены:
- `reference-prototype.html` — кликабельный референс (один файл, данные вымышленные). Это **спецификация поведения и вида, а не код для копирования**: в нём всё в одном файле и на заглушках.
- скриншот справочника из референса.

## 1. Цель продукта

Сервис сам предлагает, кого в какую группу отправить. Служитель обзванивает людей и утверждает предложение. Распределение делает сервис, человек не разбирает заявки вручную.

Главные принципы (из референса):
1. **«Сегодня» — не список задач**, а два счётчика («Готово к утверждению», «Перезвонить»), кнопка «Начать обзвон», таблица «район × возраст: места минус спрос» и один блок «Нужна помощь в сопоставлении» (ситуации, где сервис не справился, включая «не хватает группы в районе»).
2. **План строится на всю очередь сразу**, а не топ-3 для каждой заявки: учитываются вместимость групп, нехватка вариантов у «трудных» заявок, наполненность групп.
3. **Подбор работает при пропусках.** Параметров четыре: район, возраст, день/время, улица/дом. Район и возраст почти всегда есть, день/время и улица — не у всех. Считаем только по известным параметрам, уверенность падает пропорционально доле известных.
4. **Обзвон** — отдельный полноэкранный режим: одна карточка, текст разговора, кнопки «Согласился», «Не подходит» (с причиной), «Не дозвонился», «Отказ». Причина отказа запоминается как параметр человека и план пересобирается.
5. **Справочник вместо россыпи вкладок:** Группы, Люди, Координаторы — один движок отборов (фильтры, группировка, столбцы, сохранённые виды). Карточка записи выезжает поверх таблицы, а не сжимает её.
6. **Контроль** — все админские метрики (сеть, заявки, сервис подбора, кампания «40 дней»).
7. **Помощник** — раскрывающийся виджет справа внизу: ищет в базе и отвечает свободным текстом, **только читает**; действия подтверждает человек.

## 2. Как подключается база данных (важно, не придумывай другого)

Браузер к Postgres не подключается никогда. Схема такая:

```
Браузер (SPA) ──HTTP/JSON──▶ сервис dashboard (Node) ──pg Pool──▶ Postgres (контейнер db)
```

- Новая морда — **статические файлы + JSON API того же сервиса `dashboard`** (`src/dashboard/`). Второго сервера, второй базы и второго образа не заводим.
- Данные берутся через существующие репозитории `src/db/repos/*.repo.ts` и пул `src/db/pool.ts` (`DATABASE_URL`, в compose указывает на сервис `db`). SQL — только внутри репозиториев.
- Миграции накатывает **только бот** при старте. Дашборд их не накатывает. Выкладка: сначала бот, потом дашборд (`scripts/deploy.sh`).
- **Ловушка с куками.** Кука сессии ставится с `Path=/groups` (`src/dashboard/server.ts`, функция `cookie`). Поэтому и API, и SPA должны жить **под `/groups/...`**: SPA на `/groups/app/`, API на `/groups/api/v1/...`. Путь `/api/...` куку не получит. Менять `Path` на `/` нельзя: `/registration` намеренно имеет отдельный вход.
- Авторизацию, роли и лимит попыток переиспользуй (`SessionService`, `roleOf`). Вход остаётся прежним: страница `/groups` → `POST /groups/login`. SPA при ответе 401 переходит на неё.
- Удаление только у роли `super`. **Любой новый маршрут удаления добавляй в `DELETE_PATHS`** (проверка в `server.ts`), иначе он открыт обычному входу. Кнопки в интерфейсе прячь по роли, но защита — на сервере.
- CSRF-токена нет намеренно: кука `SameSite=Lax`, а изменяющие маршруты отвечают 404 на всё, кроме POST. Для новых изменяющих маршрутов сохрани это правило (никаких изменений через GET).
- Все пути из SPA в API строй от одной константы базового адреса (в Vite `base: '/groups/app/'`, API-база `/groups/api/v1/`). Не пиши относительные пути в `fetch`: страница `/groups` без косой черты уже ломала относительные адреса.
- Локальная разработка: база `docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d db` (порт 5433), дашборд `tsx` с `DATABASE_URL=postgres://church:...@localhost:5433/church40`, SPA через Vite dev server с `proxy` на `http://localhost:8090` (чтобы кука и пути совпадали с боевыми).
- Данные церкви в базе реальные (импорт таблицы: 116 групп, 233 заявки). Источник записи `groups.source` и `requests.origin` (`таблица` / `бот` / `ui`): любая правка или удаление из дашборда переводит запись в `ui`. Не ломай это в новых мутациях.
- Удаление мягкое (`archived_at`) для групп, заявок и координаторов. Жёсткое только у регистраций (`users.delete`).

## 3. Архитектура

Монорепозиторий, один образ. Структура:

```
src/
  core/matching/          чистый движок подбора (без БД и сети), тесты на нём
  db/repos/               расширяем существующие репозитории
  dashboard/
    api/                  роутеры JSON API по сущностям (requests, groups, people, coordinators, plan, control, assistant)
    server.ts             подключает api/ и раздаёт web/dist под /groups/app/
migrations/               018_... и далее, нумерация продолжает существующую
web/                      фронтенд (отдельный package.json, собственные tsconfig и тесты)
```

### Фронтенд (`web/`)
Стек: **React 18 + TypeScript (strict) + Vite**, серверное состояние через **TanStack Query**, маршрутизация **React Router**, стили — CSS-модули + дизайн-токены в CSS-переменных. Без тяжёлых UI-китов: компоненты (кнопка, чип, таблица, выезжающая панель, всплывающее окно, плашка уверенности) пишем сами.

```
web/src/
  app/            провайдеры, роутер, оболочка (шапка, вкладки, «+ Создать»)
  shared/
    api/          типизированный клиент, базовый адрес, обработка 401/403
    ui/           базовые компоненты
    filters/      движок отборов (поле, условие, значение; группировка; столбцы; сохранённые виды)
    theme/        токены и три темы: тёмная, светлая, серая (как в текущем дашборде)
    i18n/ru.ts    все тексты интерфейса (только русский)
  entities/       типы и маленькие модели: group, request, person, coordinator, plan
  features/
    today/        счётчики, таблица спроса и предложения, «Нужна помощь в сопоставлении»
    requests/     список, карточка с предложением плана, параметры подбора
    call-mode/    полноэкранный обзвон
    reference/    справочник: группы, люди, координаторы
    control/      метрики
    assistant/    виджет помощника
    create/       формы «Заявка», «Группа», «Участник» (из «+ Создать»)
```
Правила: `features` не импортируют друг друга, только `shared` и `entities`. Состояние фильтров, вкладка и открытая карточка сохраняются в адресе страницы (`?`-параметры) и переживают перезагрузку. Все цвета только через переменные, без вшитых значений.

### Движок подбора (`src/core/matching/`)
Перенеси логику из референса (`match()` и `plan()`) в чистые функции с типами и тестами **до** подключения к API:
- вход: заявки, группы, настройки весов; выход: план (`requestId → группа, оценка, уверенность, причины, запасные варианты, вытесненный вариант`), кластеры спроса, ответственные.
- веса (район 40, возраст 25, день/время 20, улица 15) вынеси в настройки, не в код;
- жёсткие отсевы: статус не «Функционирует», группа закрыта для новых, нет мест, не совпал возраст, район не совпал и не соседний;
- пропуски: параметр человека пуст — не учитываем; пуст у группы — нейтрально (0,5) и пометка «уточнить»;
- порядок обработки: сначала заявки с наименьшим числом вариантов; при близких оценках побеждает менее заполненная группа;
- поправки: −5 за подтверждение старше 30 дней, −3 если свободно одно место; уверенность = оценка × (0,55 + 0,45 × доля известных параметров);
- отказ из обзвона запоминается (исключённые группы, нежелательные дни и время) и учитывается при пересборке;
- ответственный назначается по нагрузке;
- справочник «район → соседние районы» хранится в данных, а не в коде.
Тесты: сценарий «последнее место и две заявки», пропущенные параметры, детерминированность, отказ. Проверяй тесты мутацией (сломай реализацию, убедись, что падает именно нужный тест).

### Изменения схемы (миграции `018_...` и далее, идемпотентные, с тестами на SQL)
Уже есть в `groups`: `day`, `time`, `address` (адрес «людям не давать»), `feedback_at`, `checked`, `coordinator`, `source`, `archived_at`; в `requests`: `age`, `place`, `responsible`, `recommended`, `recommended_at`, `final_group`, `group_id`, `cancel_reason`, `origin`. Проверь актуальные колонки по `migrations/` перед написанием.

- `requests`: `district text` (нормализованный район из справочника), `days text[]`, `slot text`, `street text`, `callback boolean`, `rejected_group_ids bigint[]`, `learned jsonb`, `approved_at timestamptz`.

Группы интерфейса («Готово к утверждению», «Перезвонить», «Нужна помощь», «Утверждено») вычисляются из статуса, плана и флага `callback`. Подготовь таблицу соответствия и покрой её тестами на реальных данных (импорт `dashboard/data.json`). «Утвердить» ставит `Исполнена`, `final_group`, `group_id`, `approved_at`. «Отказ» ставит `Аннулирована` и `cancel_reason`.
Нумерацию миграций продолжай; новая обязательная переменная окружения требует дописать её в серверный `.env` **до** мержа.

### JSON API (`/groups/api/v1/`)
Версионируемый контракт, типы общие с фронтом (zod-схемы на сервере, типы выводятся из них). Минимум:
- `GET plan` (план, кластеры, матрица «район × возраст»), `GET requests|groups|people|coordinators`, `GET control/{net|requests|service|campaign}`;
- `POST requests/:id/approve {groupId, shareContact}`, `/reject {groupId, reason}`, `/callback`, `/cancel {reason}`, `/params {district, days, slot, street}`;
- `POST groups/:id/verify`; создание и правка сущностей на базе существующих разборщиков форм `src/dashboard/forms.ts` (не дублируй проверки);
- `GET export/:entity.csv` для текущего отбора и столбцов;
- удаление — только `super`, адреса в `DELETE_PATHS`.
Лимит тела 64 КБ (кириллица в URL-кодировке — 6 байт на символ), JSON ужимай разумно.
Данных немного (сотни строк), поэтому первая версия отдаёт списки целиком, а фильтрация, сортировка и группировка идут на клиенте. Пагинацию не добавляй без измерений.

### Помощник (вторая очередь, за флагом `ASSISTANT_ENABLED`)
- Сервер `src/dashboard/assistant/`: языковая модель вызывает **только инструменты чтения** (поиск групп, людей, заявок, объяснение плана). Записывающих инструментов нет. Действия предлагаются кнопкой, которую нажимает человек.
- База для помощника: отдельная роль Postgres `assistant_ro` только с `SELECT` на представления (views), где телефоны маскированы, а закрытый `address` отсутствует. Ключ модели и адрес — переменные окружения; адаптер провайдера заменяем.
- Сначала сделай правило-ориентированный режим из референса (разбор «в приморском 26-35 вечером» в фильтры) как запасной вариант без модели. Подключение внешней модели согласуй с владельцем: в базе телефоны и ФИО.

## 6. Как работать

1. Сначала **план**: короткий документ (в `docs/`) с модулями, контрактом API, миграциями и этапами. Покажи его мне до кода. Если встретишь расхождение между этим промтом и кодом, сообщи, а не угадывай.
2. TDD: падающий тест, потом код. Движок подбора и разбор форм тестируются без БД.
3. Этапы (каждый — отдельный PR, зелёный CI):
   1. миграции, расширение репозиториев, `core/matching` с тестами;
   2. API `plan`, `requests`, `groups` и каркас `web/` (оболочка, темы, клиент API, вход);
   3. «Сегодня», «Заявки», карточка заявки;
   4. режим обзвона;
   5. «Справочник» с движком отборов;
   6. «Контроль»;
   7. формы создания и экспорт CSV;
   8. помощник (за флагом);
   9. паритет, документация, переключение.
4. Перед каждым коммитом: `npm run typecheck`, `npm test`, `cd web && npm run typecheck && npm test`. Линтера в проекте нет, стиль держится на `tsc` со `strict`.
5. Комментарии объясняют **почему**, а не что. Тесты называй фразой, описывающей поведение.
6. Правя поведение, обнови `README.md`, `КАК-РАБОТАЕТ-БОТ.md`, `КАК-РАБОТАЕТ-ДАШБОРД.md` (они для служителей без технического бэкграунда).
7. Мобильная вёрстка (ширина ~400 px) и три темы обязательны, горизонтальной прокрутки у страницы быть не должно (только у самой таблицы). Клавиатурная навигация и видимый фокус обязательны.

## 7. Критерии приёмки

- Служитель открывает «Сегодня», видит готовый план, нажимает «Начать обзвон», проходит очередь и утверждает группы, не заходя в «Справочник».
- План при двух заявках на одно последнее место отдаёт его той, у кого меньше вариантов или выше совпадение, и объясняет это в карточке.
- Заявка без дня/времени и без улицы получает план по району и возрасту, а уверенность ниже, чем у полной.
- «Не подходит» с причиной «другой день» исключает этот день и пересобирает предложение без перезагрузки.
- Справочник: 8 столбцов по умолчанию помещаются на экране 1280 px без горизонтальной прокрутки, карточка не сжимает таблицу, фильтры и группировка сохраняются в адресе.
- Обычный вход не может удалить запись (403 с сервера), кнопки скрыты.
- Помощник ничего не меняет в базе (проверить тестом: у роли `assistant_ro` нет прав записи).
