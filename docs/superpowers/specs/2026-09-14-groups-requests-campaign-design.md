# Дашборд домашних групп: кампания, связи заявка↔группа, переименования

Дата: 2026-09-14
Статус: утверждён пользователем, ожидает написания плана реализации.

## Контекст

Список правок от пользователя (пункты 1, 3, 4, 8, 9, 10, 11, 12 — пункты 2, 6, 7
не входят в эту сессию, пункт 5 — координаторская статистика в боте — вынесен в
отдельную спеку, так как трогает бота, а не дашборд, и требует отдельного решения
о том, как бот опознаёт координатора).

Все восемь пунктов при разборе оказались одной связанной фичей, а не восемью
независимыми: домашние группы и заявки сейчас связаны только свободным текстом
(`groups.leader`/`phone`, `requests.recommended`/`final_group`/`responsible`), и
почти все пункты так или иначе про то, чтобы сделать эту связь настоящей и
подтянуть уже собранные ботом данные туда, где дашборд их пока не показывает.

## 1. Реестр групп — бейдж «40 дней» и фильтр

Новый столбец сразу после «Группа» (перед «Район»): `<span class="pill live">40
дней</span>`, если у группы есть совпадение — переиспользуем существующий зелёный
CSS-класс `.pill.live` (уже используется для статуса «Функционирует»), новых
стилей не заводим. Пусто, если совпадения нет.

Условие совпадения: существует `users` с `complete = true`, чей нормализованный
телефон (`normalizePhone`, как в `fsm.ts`) входит в `groups.phones[]` (тот же
массив, что уже использует `activeLeaderByPhone`).

Фильтр — тот же паттерн, что и существующий переключатель статуса
(`segStatus`): три кнопки «Все / Зарегистрированы / Не зарегистрированы» над
таблицей реестра.

### Дубль номера на время кампании

Правило «один активный ведущий — один номер» (`groups.repo.ts:220`,
`activeLeaderByPhone`) живёт только в потоке бота («готов открыть группу» /
«готов предоставить дом», `router.ts:leadPhoneTaken`). У дашбордской формы
«Добавить → Новая домашняя группа» такой проверки нет и не было — там дубль по
номеру уже работает сегодня.

Меняем: пропускаем проверку `activeLeaderByPhone` внутри `leadPhoneTaken`, пока
`campaignDay(now, cfg)` в диапазоне `[1, CAMPAIGN_DAYS]` — переиспользуем
готовую функцию из `schedule.ts`, новой работы с датами не пишем. До начала
кампании и после её 40 дней правило действует как раньше.

Второй чек в том же методе, `openLeadByPhone` (не даёт подать две одновременные
*заявки* с одного номера), не трогаем — это защита от повторного нажатия, а не
от второй группы.

## 2. Подбор ведущего при создании/правке группы

Новый метод `UsersRepo.leaderCandidates()`: участники с `mdg_status IN ('open',
'home')` и `complete = true` (готов открыть Малую группу / готов предоставить
свой дом). Отдаём в `DashboardData` рядом с уже существующим `coordinators`.

В форме группы (`GROUP_FIELDS`) над полем «ФИО ведущего» — обычный `<select>`
(без поиска: пул кандидатов небольшой), каждый пункт списка показывает полный
профиль в порядке из примера пользователя: `ФИО · Телефон · Церковь · статус
(готов открыть / готов предоставить дом) · Район · Возраст`. Выбор автоподставляет
существующие текстовые поля «ФИО ведущего» и «Телефон» — новой связи в базе не
заводим: бейдж из раздела 1 сработает сам по факту совпадения телефона.

## 3. Код домашней группы

Без изменений схемы: `'ДГ-' + String(id).padStart(4, '0')` (например, `ДГ-0114`),
вычисляется на фронтенде из уже существующего `groups.id`. Показывается рядом с
именем ведущего в реестре и в опциях группового пикера из раздела 4 — там он
нужен, чтобы различать группы с похожими фамилиями ведущих.

## 4. Заявки — колонка «Домашняя группа», рекомендация, принудительное назначение

Новая миграция `010_requests_group_link.sql`:

```sql
ALTER TABLE requests ADD COLUMN group_id bigint REFERENCES groups(id);
CREATE INDEX requests_group_idx ON requests (group_id) WHERE group_id IS NOT NULL;
```

Один столбец обслуживает и рекомендацию, и назначение:

- **Рекомендация** — в раскрытой строке заявки `<select>` со всеми активными
  (`archived_at IS NULL`) группами; группы, чей `age` пересекается с возрастом
  заявки, идут первыми/помечены — переиспользуем и расширяем существующий
  `ageBucket()`/`AGE_BUCKETS` из дашбордского JS вместо нового парсинга возраста.
- **Принудительное назначение** — тот же `<select>` позволяет выбрать любую
  группу, не только рекомендованные; это и есть «принудительно», без отдельного
  поля-дублёра.

Видимый столбец `<th>Домашняя группа</th>` в таблице заявок показывает
привязанную группу (имя ведущего + код `ДГ-XXXX`). Фильтр над таблицей — обычный
`<select>` по группам (групп может быть 100+, поиск не нужен, обычный select
достаточно).

Если группа, на которую ссылается заявка, впоследствии архивируется — заявка
продолжает показывать её как есть (связь не рвём, в список *новых* назначений
архивная группа просто не попадает).

## 5. «Ответственный» — скрыт как столбец, стал выпадающим списком

`<th>Ответственный</th>` убираем из таблицы заявок (на его месте — «Домашняя
группа» из раздела 4). Поле остаётся только в раскрытой строке/форме правки, но
из свободного текста становится `<select>`, источник — уже существующая и уже
подгружаемая на фронтенд таблица `coordinators` (сейчас используется только для
счётчика на плитке, впервые задействуем по назначению).

Подстраховка: если текущее значение `responsible` не входит в список активных
координаторов (опечатка, координатор архивирован), оно добавляется в список
отдельным пунктом — иначе сохранение строки молча заменило бы его на первый
пункт списка.

## 6. «Куда направляем»

Просто выводим уже существующее поле `requests.recommended` (сейчас видно
только в раскрытой строке) отдельным видимым `<th>Куда направляем</th>` в
таблице заявок. Новых полей и фильтра не заводим — фильтр не запрашивался.

## 7. Переименования

- Вкладка «Обзор» (`data-view="all"`) → «Домашние группы».
- Вкладка «Заявки» (`data-view="requests"`) → «Заявки (МДГ)», включая заголовок
  карточки `<h2 class="card-title">Заявки</h2>` внутри этой секции.

## Вне рамок этой спеки

Пункт 5 (минимальная статистика для координаторов в самом боте) — отдельная
спека: у координаторов сегодня нет способа подтвердить свою личность в чате
(`coordinators` — это просто имя+роль, без `chat_id`, в отличие от `ADMIN_IDS`),
это отдельное архитектурное решение, не UI-правка.

## Принятые допущения (можно поправить без пересмотра остального)

- Бейдж «40 дней» — по буквально завершённой (`complete = true`) регистрации
  участника, не по любой начатой анкете.
- Окно ослабления запрета на дубль номера — строго `CAMPAIGN_START_DATE .. +
  CAMPAIGN_DAYS`, не «навсегда».
- Подбор ведущего — обычный `<select>`, без автокомплита/поиска.
- Рекомендация группы по заявке — только по возрасту, без учёта района.
- Код группы — вычисляемый, без нового столбца/счётчика в базе.
