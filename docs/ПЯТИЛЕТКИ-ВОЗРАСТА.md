# Пятилетки возраста групп — проектирование (этап 0)

Статус: **проектирование, кода ещё нет.** Цель документа — спроектировать переход
«широкие категории возраста → пятилетки» так, чтобы не сломать существующее, и зафиксировать
все решения и риски до написания кода.

## 1. Цель и рамки

**Делаем:** возраст **группы** становится набором пятилетних диапазонов без задвоения
(несколько можно отмечать галочками, как сейчас).

**Не трогаем (намеренно):**

- Анкету **человека** в боте — её категории остаются прежними. Это значит, **бот не меняется**.
- Сам движок подбора — он уже работает на числовых диапазонах, а не на названиях категорий
  (см. §3).
- Матрицу «Сегодня» — её колонки остаются колонками анкеты человека.

## 2. Текущее состояние (факты)

Категории возраста человека (анкета бота, `src/core/texts.ts:327`, `AGE_GROUPS`):

```
['подростки (до 18 лет)', '18-25', '25-40', '40-55', '55-65', '65+']   // 6 значений
```

Эти же значения используются как возраст **группы**: форма группы (`src/home-groups/create.ts:218`
`ageGroups: [...AGE_GROUPS]`), разбор (`groupAgeCategories` в `src/home-groups/plan/parse.ts`),
миграция `068` (SQL-двойник `group_age_categories`).

Колонки матрицы «район × возраст» (`src/home-groups/plan/parse.ts:28`, `AGE_COLUMNS`) —
параллельный список тех же 6 категорий.

Разбор текста в диапазон — `ageRange` в `src/core/matching.ts:77`:
«35-45 лет» → `[35,45]`, «65+» → `[65,120]`, «подростки» → `[12,17]`, «40» → `[40,40]`,
«любой»/пусто → `null` («не знаем»).

## 3. Ключевое наблюдение (почему это безопасно)

Подбор сравнивает возраст **числовыми диапазонами**, а не строками категорий:

- `src/home-groups/plan/engine.ts:79-80`: группа не подходит, если
  `g.ageRanges.some(range => overlaps(age, range))` ложно.
- `overlaps = a[0] <= b[1] && b[0] <= a[1]` — включительное пересечение.
- Диапазоны группы получаются из `parseGroupAgeRanges(g.age)`, диапазон человека — из
  `parseAgeRange(r.age)`.

Следствие: **смена набора «ярлыков» возраста группы не меняет логику подбора.** Меняются
только: (а) набор ярлыков и их диапазоны, (б) как строка `groups.age` раскладывается в эти
ярлыки.

Второе следствие (важно для миграции): жёсткий отсев по возрасту — это
«группа **не** подходит». **Расширение** диапазона группы даёт лишь больше кандидатов, которых
всё равно утверждает координатор; **сужение** — молча выбрасывает подходящих людей. Поэтому
при перераспределении выбираем правило «никогда не терять возраст» (см. §5).

## 4. Решения (согласовано)

### Р1. Пятилетки только у групп; у человека категории не меняются

Анкета бота не меняется (выполняем «пока бота не трогаем»), матрица «Сегодня» остаётся с 6
колонками спроса, подбор работает через пересечение диапазонов. Списки возраста группы и
человека **разводятся** на два отдельных.

### Р2. Границы пятилеток (согласовано: края оставляем, 18–25 режем, без задвоения)

Набор из 12 значений; каждый возраст попадает ровно в один диапазон:

| № | Категория | Возраст |
|---|---|---|
| 1 | подростки (до 18 лет) | 0–17 |
| 2 | 18–20 | 18–20 |
| 3 | 21–25 | 21–25 |
| 4 | 26–30 | 26–30 |
| 5 | 31–35 | 31–35 |
| 6 | 36–40 | 36–40 |
| 7 | 41–45 | 41–45 |
| 8 | 46–50 | 46–50 |
| 9 | 51–55 | 51–55 |
| 10 | 56–60 | 56–60 |
| 11 | 61–64 | 61–64 |
| 12 | 65+ | 65+ |

Примечание: «18–20» (3 года) и «61–64» (4 года) — следствие того, что края «до 18» и «65+»
не ложатся на сетку «21–25, 26–30, …». Остальные диапазоны — ровно по 5 лет.

Стыки подтверждены: верхний — «61–64 / 65+» (буквально «65 и старше»), нижний — «18–20»
(3 года) как часть разрезанного «18–25».

### Р3. Разложение существующих записей

Строка `groups.age` переписывается в набор пятилеток, который эта строка «задевает».
Правило — **включительное пересечение, ничего не теряем** (см. §5). Потеря точности только в
сторону «мельче», а граничные возраста не выбрасываются.

### Р4. Матрица «Сегодня» не меняется

Колонки остаются колонками человека (6). Места групп (пятилетки) по-прежнему раскладываются
в них через `ageColumnsOverlapping`, поэтому спрос и места остаются сопоставимыми.

## 5. Целевая модель и алгоритм разложения

Вводим **отдельный** список пятилеток группы (12 значений) с границами. Благодаря «без
задвоения» алгоритм проще текущего: не нужны ни правило «касание в одной цифре не считается»,
ни «нижняя категория» — каждый возраст в ровно одном диапазоне.

- `GROUP_AGE_BUCKETS` — 12 ярлыков (таблица из §4 Р2).
- `GROUP_AGE_RANGES` — включительные границы тех же 12:
  `[0,17],[18,20],[21,25],[26,30],[31,35],[36,40],[41,45],[46,50],[51,55],[56,60],[61,64],[65,120]`.

Алгоритм `groupAgeCategories(raw)`:

1. `raw` пусто / «любой» / мусор → `null` (возраст неизвестен, не трогаем).
2. `raw` — уже каноничный список пятилеток (все части ∈ `GROUP_AGE_BUCKETS`) → вернуть в
   каноничном порядке (идемпотентно).
3. Иначе разобрать `ageRange(raw)` → `[lo, hi]`:
   - одно число (`lo === hi`) → тот диапазон, в который число попадает (единственный);
   - иначе → все диапазоны, с которыми `[lo, hi]` пересекается (включительно):
     `lo <= b_hi && b_lo <= hi`.
4. Если не нашлось — вернуть `null` (не знаем, оставить как было).

Тот же алгоритм реализуется в SQL (`CREATE OR REPLACE FUNCTION group_age_categories`) —
SQL и TS обязаны совпадать и проверяться тестом (см. §7).

Примеры разложения:

| Было | Стало |
|---|---|
| «18-25» | «18-20, 21-25» |
| «25-40» | «21-25, 26-30, 31-35, 36-40» |
| «40-55» | «36-40, 41-45, 46-50, 51-55» |
| «55-65» | «51-55, 56-60, 61-64» |
| «35-40» | «31-35, 36-40» |
| «35-50» | «31-35, 36-40, 41-45, 46-50» |
| «40» (одно число) | «36-40» |
| «любой» / пусто | без изменений |

Граничные возраста не теряются (например, «25» из «25-40» попадает в «21-25»), но диапазон
слегка расширяется до полной пятилетки («25-40» → «21-40»). Это осознанная плата за «не
потерять» — подробнее в §3. После миграции координаторы выборочно сверят возраст групп,
которые упирались в границы категорий.

## 6. Миграция существующих данных

Новая миграция `073_group_age_five_years.sql` (идемпотентная, в духе `068`):

1. `CREATE OR REPLACE FUNCTION group_age_categories(raw)` с 12 пятилетками.
2. `UPDATE groups SET age = group_age_categories(age) WHERE group_age_categories(age) IS NOT NULL AND group_age_categories(age) IS DISTINCT FROM age;`
3. `normalize_group_fields()` — **переопределить целиком** так же, как в `068`: она уже вызывает
   `group_age_categories`, поэтому после `CREATE OR REPLACE` повторный перенос Google-таблицы
   тоже раскладывает возраст в пятилетки и не возвращает старые широкие значения. Части из
   миграций `046`/`047`/`068` внутри `normalize_group_fields()` перенести без изменений.
4. Идемпотентность: каноничная запись (уже пятилетки) остаётся как есть.

Атомарность с кодом: TS-разбор (`groupAgeCategories`) и SQL должны выйти **в одном PR/деплое**.
Порядок деплоя уже правильный: бот накатывает миграцию, потом поднимаются `dashboard` и
`home-groups` (см. `scripts/deploy.sh`).

## 10. Риски и откат

- **Окно несоответствия при деплое** (между накатом миграции и подъёмом `home-groups`):
  старый разбор увидит новые строки «21-25, 26-30» как неизвестный возраст → группы временно
  «возраст не указан» (без отсева по возрасту). Окно секунды (деплой идёт по порядку),
  данные не теряются. Приемлемо, но зафиксировать.
- **Расширение на границах**: «25-40» → «21-40» и т.п. Это безопаснее сужения (§3), но
  координаторам стоит выборочно проверить группы, чей возраст упирался в границы категорий.
- **Откат**: пятилетки → широкие категории обратимы (обратная свёртка), но не автоматически.
  Стратегия: либо обратная миграция `073_revert`, либо редеплой старого кода + обратный
  `UPDATE`. Заложить в описание PR.
- **Дублированные списки**: возраст есть в `texts.ts`/`parse.ts`/SQL/старом дашборде/фильтрах.
  Меняем только список **группы**; список человека (`AGE_GROUPS`) и матрицу (`AGE_COLUMNS`)
  не трогаем — это и есть защита от разъезда.
